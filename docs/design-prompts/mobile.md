## 0. 依頼の要約

| 項目 | 内容 |
| --- | --- |
| プロダクト | 冷蔵庫の在庫を登録すると、その在庫で作れる**献立**を提案する個人向けアプリ |
| 対象 | **iOS / Android のネイティブアプリ。スマートフォンが主、タブレットも対応** |
| 成果物 | 画面デザイン一式（下の「9. 成果物」の一覧）＋ 配色・書体・余白のデザイントークン |
| 最優先 | **台所で、疲れて帰宅した人が、片手で、考えずに選べること** |
| 未確定なので**あなたが決めてよいもの** | 文言・配色・書体・余白・寸法・アイコン・アニメーション・ハプティクス |
| **絶対に変えてはいけないもの** | 画面の構造・状態・要素の優先順位・用語（3章の禁止語） |

サーバとの関係は前提として固定です。**アプリは HTTP API のクライアントであり、業務ロジックはサーバにあります。**
とくに **AI の呼び出しは必ずサーバ経由**で、アプリから直接 AI を呼ぶ画面（API キーの入力欄など）は存在しません。

## 1. このプロダクトが何を解こうとしているか

**「今日何作ろう」を考える手間をなくす。** これが唯一の目的です。

- 献立が決まらないのは選択肢が多いからではなく、**「今ある食材」という制約を思い出しながら考えないといけない**から。
- レシピサイトは「作りたい料理」から探す作りで、「今あるもので何が作れるか」の方向を向いていない。
- 結果、決めるのを諦めて外食・惣菜になる。

> **在庫管理は手段であって目的ではない。** 在庫の画面を作り込む方向に寄せないでください。在庫を登録する見返りは「献立が決まること」であり、それが画面の主役です。

### 想定利用者

| 項目 | 内容 |
| --- | --- |
| 誰 | 30代・共働き会社員。1人で使う（家族共有は将来対応で、いまは作らない） |
| 状況 | 平日の帰宅は20時前後。週末にまとめ買い |
| 課題 | 帰宅時点で疲れており、献立を考える気力がない。冷蔵庫を開けて眺めても決まらない |
| 期待 | 「今ある食材でこれが作れる」を、**考える前に**提示してほしい |
| 使う場所 | **台所。片手。立ったまま。手が濡れている／汚れていることもある** |

### 成功の判断基準

1. 週に数回、実際に開いて使うか
2. 提示されたものから「これにしよう」と決められるか
3. **在庫の登録が、面倒で放置されるほどの負担になっていないか**

3 が最大の離脱要因です。**登録の手間を増やす設計は、それだけで却下されます。**

## 2. やらないこと（画面に出してはいけないもの）

以下はスコープ外です。**気を利かせて足さないでください。**

- 栄養計算・カロリー・健康アドバイス
- 食品ロス削減の集計・レポート・バッジ
- 買い物リストの自動生成、ネットスーパー連携、価格比較
- 家族間のリアルタイム共有、招待、権限
- レシピの投稿・共有・いいね等のコミュニティ機能
- **バーコードスキャン、レシート OCR、カメラ連携**（ネイティブなら自然に思いつきますが、**スコープ外です**）
- 献立の編集（**生成された献立は編集できません**）
- 食材の「保存場所」（冷蔵/冷凍/野菜室）という入力項目 — **意図的に持ちません**
- **オフラインでの登録・編集。** オフライン時は書き込み操作を止めます（ローカル DB を持って後から同期する設計にはしません）
- 並べ替えの選択肢（在庫は期限順に固定）
- ウィジェット・ウォッチアプリ・Siri / アシスタント連携（**今回は対象外**）

## 3. 用語 ★ 最重要・例外なし

このプロダクトは、日本語の語とコード上の識別子を1対1で固定しています。
**UI 文言もこの表に従います。** 同義語を混ぜると、この先の実装と会話がすべて壊れます。

| 日本語（UI に出してよい語） | 意味 |
| --- | --- |
| **献立** | 生成された1つの献立。名称・材料・手順を持ち、保存される |
| **提案** | 1回の提案で得られた献立1〜3件のまとまり |
| **材料** | 献立が必要とする食材と分量 |
| **手順** | 調理の1ステップ |
| **在庫** / **在庫品** | 冷蔵庫にある食材1件 |
| **食材** | 「にんじん」のような食材の種類 |
| **分量** | 「200g」「1本」「大さじ2」。**自由文字列** |
| **期限** | 使い切りたい日。賞味期限と消費期限は区別しない |
| **不足** | 現在の在庫で賄えない材料 |

### 使ってはいけない語（UI 文言・見出し・ボタン・空状態の文、すべて）

> **レシピ / Recipe / メニュー / Menu / 候補 / 料理 / ストック / アイテム / フード / 献立案**

「おすすめレシピ」「今日のメニュー」「候補が3件」「料理を選ぶ」——**すべて不可**です。
言い換えの例: 「献立」「今日の献立」「提案」「作れる献立」。

**アプリ名・アイコン下のラベル・通知の文面・App Store / Google Play のスクリーンショット文言にも同じ制約がかかります。**

## 4. 画面仕様

### 4.1 ナビゲーション

主要な移動先は3つ。**タブバー**に置きます（片手で親指が届く位置に主要な移動手段を集める）。

| タブ | 中身 |
| --- | --- |
| **献立** ★中心 | 今日の提案。**起動時に開く画面** |
| **在庫** | 冷蔵庫にあるものの一覧と登録 |
| **履歴** | 過去の献立 |

- **設定は独立したタブにしません。** 履歴タブの右上に入口を置きます（中身はログアウトとアカウント削除だけで、タブの1枠を使う価値がない）。
- 起動時に開くのは「在庫」ではなく **「献立」** です。開く動機が「何を作るか知りたい」だからです。
- タブバーの位置は iOS / Android それぞれの慣習に従って構いません（Android で bottom navigation bar、iOS で tab bar）。**3つという数と割り当ては変えないでください。**

### 4.2 献立タブ ★ この画面が中心

提案は **1〜3件で変動します。** これは不具合ではなく仕様です。

献立には2つの出どころがあり、**1つの提案の中で混ざりません。**

| 出どころ | 何か | 表示 |
| --- | --- | --- |
| **再利用** | 過去に見た献立のうち、**今日の在庫で不足0件**のもの | **印を付ける**（「前に見たこれ、今日の在庫で作れます」という意味） |
| **生成** | AI が今の在庫から新しく作ったもの。常に3件を求める | **印を付けない** |

> 両方に印を付けると印が背景になって消えます。**片方だけに付けるから目に入ります。**

#### 持つべき状態（すべてデザインしてください）

| # | 状態 | 条件 |
| --- | --- | --- |
| S-1 | 提案あり（**再利用**） | 作れる既存の献立が1〜3件。印つきカードが並ぶ |
| S-2 | 提案あり（**生成**） | 新しく生成した1〜3件。印なし |
| S-3 | 保存済みの提案 | 在庫が前回から変わっていない。**見た目は S-1 / S-2 と同じ**（利用者に説明する必要がない） |
| S-4 | **在庫が足りない** | 在庫が0〜1件。献立を出せない。**在庫の登録に送る** |
| S-5 | **生成中** | 明示操作の直後。**数十秒かかる** |
| S-6 | **生成に失敗** | AI の応答が使えなかった／API エラー。**前の提案を残したまま**、再試行の手段を出す。自動で再試行しない |
| S-7 | **上限に達した** | 1日の生成回数の上限（初期値10回）に達した |

#### 画面に置くもの（上から）

1. 献立カード（1〜3件）
2. **「新しい献立を見る」に相当するブロック** — 常に最後
3. **注意表示** — 「AI による提案です。分量・加熱時間はご自身で確認してください」に相当するもの。**画面末尾に1回だけ**（カードごとに繰り返すと読まれなくなる）

#### 献立カードに載せるもの（この3つだけ）

- 献立の名称（30字以内）
- **材料の件数と不足の件数**（「不足なし」または「不足2件」）。※ この件数は**調味料を除いた主材料で数えます**
- **使う食材を2〜3件**。期限が近いものを優先して見せる。期限が今日のものには名称の後ろに「(今日)」に相当する表記を添える（**色だけに頼らない**）

> **材料を全部並べないでください。** カードが縦に伸びると3件を見比べられなくなります。内訳は詳細画面の仕事です。

#### 「新しい献立を見る」ブロックの要件

- **テキストリンクではなく、献立カードと同じ大きさの面**にする。提案が1件の日でも画面が空白に見えないため、かつ押せることを迷わせないため
- 押すと**必ず AI を呼ぶ**（再利用しない・常に3件を新しく作る）
- **費用と待ち時間が発生する操作なので、「数十秒かかります」に相当する予告を押す前に見せる**
- S-4（在庫が足りない）のときは**出さない**。押しても動かない操作を置かない
- **引っ張って更新（pull to refresh）に、この生成を割り当てないでください。** 費用と数十秒の待ちが発生する操作を、偶発的に起こせる場所に置かない

#### 件数が1件の日でも、空き枠を作らない

3枠のうち2枠をプレースホルダで埋めると「壊れている」と読まれます。**カードを詰めて並べ、末尾のブロックが常に最後に来ることで画面としての収まりを作ります。**

#### 生成中（S-5）

- **押した瞬間に画面を空にしない。** 前の提案を薄くでも残す
- 進行中であることと**経過時間**が分かる表示（数十秒待たされるため）
- 失敗しても前の提案がそのまま残っていれば、利用者は何も失わない
- **生成中に他のタブへ移動できてよいか**を設計判断として示してください（移動できる場合、戻ったときに何が見えるか）

### 4.3 献立詳細

献立タブからも履歴タブからも入ります。**内容は生成時のまま不変です**（開くたびに変わってはいけない）。

載せるもの:

- 献立の名称
- **材料（2人分）** — 主材料が先、調味料が後。上から読んでその献立の中身が分かる並び
  - 賄える主材料: `✓` に相当する印
  - 不足する主材料: `✗` と「不足」に相当する印。**記号と文字の両方**で区別する
  - **調味料には印を付けない。** 在庫と照合していないという意味。「賄える」とも「不足」とも表示しない
- **手順** — 3〜6ステップ、1ステップ60字以内の短文
- **注意表示**（AI による提案／分量・加熱時間は自分で確認）。**詳細画面では必ず出す**
- **「これを作った」に相当する記録操作**

決まっていること:

- 充足（賄える／不足）は**開くたびに計算し直す**。1週間前の献立を履歴から開いても、判定は今日の在庫で行う
- 記録操作は**取り消せない**。ただし**確認ダイアログは出さない**（押し間違えても実害がなく、1タップ増える害の方が大きい）
- 記録済みの献立を再度開いても、**同じ位置に同じ操作がある**（もう一度作れる）。すでに記録があることが分かる表示にする
- **「作った」を記録しても在庫は自動で減りません。** 「在庫を減らしますか?」とは聞かない

ネイティブならではの検討点（提案してください）:

- **手順を見ながら調理する**画面です。手が離せない状況で読めるか（文字サイズ・行間・スクロール量）
- 画面を消さずに置いておきたい場面がありますが、**常時点灯のトグルを足すかどうかは判断を仰いでください**（新しい設定項目になるため、勝手に足さない）

### 4.4 在庫タブ

```
在庫                                  ＋
[すべて] [肉] [野菜] [その他]

⚠ 期限 今日まで
   豚こま肉     300g    今日
   小松菜       1束     今日

期限が近い
   白菜        1/4個   あと2日
   卵          6個     あと5日

その他
   にんじん     2本     あと12日
   乾燥わかめ   1袋     －
```

- **既定は期限の近い順**。並べ替えの選択肢は置かない
- **期限で3つの帯に分ける。帯の見出し自体がテキストの警告**になっているので、色を使わなくても意味が通る
- 期限は「今日」「あと2日」のような**残日数のテキスト**で出す。未設定は「－」に相当する表示で、末尾の帯に置く（**警告の対象外**）
- 削除は**行のスワイプ。確認は出さない**（登録し直すコストが低いため）
- **同じ食材名の行が複数並ぶことがあります。** 買った日が違えば別の在庫として扱うためで、**仕様であって不具合ではありません**
- カテゴリの絞り込みは優先度が低い（数十件の規模では絞る必要が薄い）。**あってよいが、主役にしない**
- 在庫0件の空状態は、**献立が出せない状態と地続き**であることが伝わるようにする

### 4.5 食材の登録・編集

**「名前を入れてから保存まで10秒以内」が設計の制約です。**

```
← 食材を追加

食材名
[ にん                    ]
  にんじん
  にんにく

分量（任意）      期限（任意）
[ 2本        ]   [ 9/12      ]

[     保存してもう1件      ]   ← 主ボタン
        保存して閉じる          ← 副
```

- **主ボタンは「保存してもう1件」に相当するもの。** 買い物後にまとめて入れるのが主な使い方で、1件だけ足すのは例外
- **分量も期限も任意。** 必須にしない
- 食材名は入力途中でマスタから補完される。ただし**補完に出てこない名前もそのまま登録できる**（補完は入力を助けるだけで、登録を止めない）
- 保存場所の入力項目は**ない**

ネイティブならではの検討点:

- **ソフトキーボードが出ている状態が、この画面の既定**です。キーボードに隠れない位置に主ボタンと補完候補を置いてください
- 連続入力（「保存してもう1件」）のあと、**キーボードを閉じずに次の1件へ入れる**流れにしてください
- 期限の入力は日付ピッカーで構いませんが、**開く手数が増えないこと**を優先してください
- 画面の形は**全画面にするか、シート（ボトムシート/モーダル）にするか**を判断し、根拠を添えてください

### 4.6 履歴タブ

```
履歴                                  ⚙
[ 以前見た献立 | つくった献立 ]

  豚こま肉と白菜の生姜焼き
  9/5 · 材料5件

  にんじんと卵の炒めもの
  9/3 · 材料3件
```

- 2つの一覧は**同じ献立を「作った記録があるかどうか」で振り分けたもの**。**一度作った献立は「以前見た」から消えて「つくった」に移ります**（両方には出ません）
- 新しい順
- **一覧には充足状況を出さない**（開いたときに計算すれば足りる）
- 設定への入口をここに置く

### 4.7 認証・設定

| 画面 | 中身 |
| --- | --- |
| ログイン / サインアップ | 外部の認証基盤に委譲。メールアドレスとパスワードを想定。パスワードは自前で持たない |
| 設定 | ログアウト、**アカウントとデータの削除** |

**アカウント削除は確認を必須にします。** 取り消せず、在庫・献立・作った記録がすべて消えるため。
（「これを作った」が確認なしなのと**逆の判断**である点に注意してください。取り消せるか・実害があるかで分けています。）

> iOS の App Store は、アカウント作成があるアプリに**アプリ内からのアカウント削除**を要求します。上の設定画面がそれを満たす前提で設計してください。

### 4.8 画面をまたぐ規則

| 事象 | 扱い |
| --- | --- |
| **オフライン** | 画面上部に帯で明示し、**書き込みを伴う操作を無効化する**。閲覧は続けられる。**オフラインでの登録は行わない**（後から同期しない） |
| **AI の障害・上限** | **在庫と保存済みの献立は通常どおり使える。** 生成だけが止まり、その旨を伝える |
| 生成の失敗 | 前の提案を残したまま再試行の手段を示す。**自動で再試行しない** |
| 期限の表現 | 色に加えて**必ずテキスト**（「今日」「あと2日」）を併用する |
| 初回起動 | 在庫0件なので献立タブは S-4。**在庫の登録に送る** |

## 5. 画面に出るデータの形

```
献立 {
  名称:   文字列（30字以内）
  材料:   1〜12件。各件 { 名前, 分量（自由文字列）, 種別: 主材料 | 調味料 }
  手順:   3〜6件。各件 60字以内の1文
  作った記録: 0件以上（0件なら「以前見た」、1件以上なら「つくった」）
}

在庫品 {
  名前:   文字列（自由入力可）
  分量:   「300g」「1/4個」など。未設定あり
  期限:   日付。未設定あり
}

提案 {
  献立: 1〜3件（0件はない）
  各件の出どころ: 再利用 | 生成（1つの提案の中で混ざらない）
}
```

表示に使えるサンプル（そのまま使って構いません）:

- 献立名: 「豚こま肉と白菜の生姜焼き」「にんじんと卵の炒めもの」「鶏むね肉ときのこの蒸し煮」「厚揚げと小松菜の煮びたし」

## 6. 非機能要件（デザインに効くもの）

| # | 要件 |

## 7. プラットフォームとタブレット（この依頼の固有部分）

### 7.1 iOS と Android

- **両プラットフォームのデザインを出してください。** 画面の構造・状態・情報の優先順位は共通、**表現は各プラットフォームの慣習に寄せる**方針です（ナビゲーションバー、戻る、シート、スイッチ、ダイアログ、タイポグラフィ）
- **Android のシステムの戻る操作**（ジェスチャー／ボタン）で何が起きるかを、画面ごとに示してください。とくに**生成中（S-5）に戻ったとき**の挙動
- iOS のスワイプバック、Android の戻るで**「これを作った」の記録が取り消されることはありません**（記録は取り消せない）
- セーフエリア（ノッチ、ホームインジケータ、ステータスバー）を明示してください
- **ダークモードは両 OS で必須**として扱ってください（**台所で夜に使う**アプリです）
- ハプティクスを使う場所があれば提案してください（例: 生成の完了）

### 7.2 タブレット

スマートフォンが主用途で、**タブレットは「台所に据え置いて手順を見る」使い方**を想定します。

- **献立一覧と献立詳細の2ペイン（リスト＋詳細）**を検討してください。採否は根拠つきで
- タブバーをそのまま使うか、**サイドナビに置き換えるか**を判断し、根拠を添えてください
- 横向き（landscape）でのレイアウトを必ず示してください。**手順を見ながら調理する画面が横向きで読みやすいこと**を優先
- 幅を広げたときに、**献立カードを横に並べる**のか、1カラムのまま最大幅で止めるのかを決めてください
- **片手操作の要件はタブレットには適用しません**（据え置き前提）。ただしスマートフォンでは絶対です

### 7.3 通知（優先度が低い機能）

- 期限が近い食材のプッシュ通知は**優先度の低い将来機能**です。**通知許可を求める画面を初回起動に置かないでください**
- 通知の文面と、通知から開いたときの着地点を**1案だけ**提案してください（実装するかは未定）

### 7.4 アプリの外形

- アプリアイコン（iOS / Android 両方の形式）
- スプラッシュ／起動画面
- App Store / Google Play のスクリーンショット1〜3枚の方向性（**禁止語を使わない文言で**）

## 8. すでに決まっていること / あなたが決めること

### 変えてはいけない（変えたいなら、実装前に質問してください）

- 3章の**用語と禁止語**
- 提案が**1〜3件で変動する**こと、**再利用と生成が混ざらない**こと、**再利用にだけ印が付く**こと
- **生成は明示操作でしか起きない**こと（自動再生成しない／引っ張って更新に割り当てない）
- 献立が**編集できない**こと、**充足を毎回計算し直す**こと
- **「作った」を記録しても在庫が減らない**こと
- 在庫が**期限順固定**であること、**同名の行が並びうる**こと
- **オフラインで書き込まない**こと
- 「これを作った」は確認なし／**アカウント削除は確認あり**
- 4章の各画面が持つ**状態の一覧**

### あなたが決めてよい（むしろ提案してほしい）

- **文言すべて。** この依頼文の「今日の献立」「新しい献立を見る」「前に見た献立」「これを作った」等は**すべて仮置き**です。禁止語を使わない限り、より良い案を出してください。とくに次の3か所は伝えるべき意味だけが決まっていて、書き方が未決です:

  | 箇所 | 伝えるべきこと |
  | --- | --- |
  | 生成を起こす操作 | 押すと新しい献立が作られること。**数十秒かかること** |
  | 再利用の印 | 前に見た献立であり、**今日の在庫で作れる**こと |
  | 注意表示 | AI による提案であり、**分量と加熱時間は自分で確認する**必要があること |

- 配色・書体・余白・寸法・角丸・影・アイコン・モーション・ハプティクス
- 再利用の印の形（バッジ・アイコン・色・位置）
- 期限の3段階（今日まで／近い／その他）の視覚表現
- 登録画面をシートにするか全画面にするか、タブレットの2ペイン構成

## 10. 迷ったときの判断基準

1. **在庫より献立を優先する。** 在庫管理は手段であって目的ではない
2. **登録の手間を増やす案は却下。** 入力項目を足したくなったら、まず疑う
3. **押せない操作を置かない。** 動かない状態のボタンを出すくらいなら、その場に別の導線を置く
4. **色だけで意味を伝えない。** 例外なし
5. **件数が減ることを隠さない。** 空き枠やプレースホルダで3件に見せかけない
6. **費用と待ち時間のかかる操作を、偶発的に起こせる場所に置かない**
7. 判断がつかない場合は、**推測で決めずに質問してください**
