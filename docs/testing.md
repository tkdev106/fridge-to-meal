# テスト方針

このリポジトリのテストは **AI が書き、AI が読み、AI が壊れたことに気づくためのもの**である。
人が1コマンドずつ見ていないため、**テストが嘘をつくと誰も気づけない。** 本書は
「どうテストするか」を定める。進め方（ブランチ・完了の定義）は `docs/workflow.md`、
何を作るかは `docs/requirements.md`、どう表現するかは `docs/domain-model.md` が担う。

TDD の1周を回すのは `/tdd` と3つのサブエージェント（`test-designer` → `test-writer` →
`implementer`）。**3者が共通の根拠として読むのが本書である。**

---

## 1. 4つの柱と、譲らないもの

| 柱 | 内容 | このリポジトリでの担保 |
| --- | --- | --- |
| 退行の検出力 | 壊れたら赤くなる | 不変条件と確定事項 C-n を必ず1つ以上のテストで押さえる |
| **リファクタリング耐性** | **壊れていないのに赤くならない** | **観察可能な振る舞いだけを検証する（第3章）** |
| 速さ | すぐ返る | プロセス外の依存を使わない（第5章） |
| 保守しやすさ | 読んで意図がわかる | 1テスト1振る舞い。本題以外はヘルパーに隠す（第6章） |

**4つは同時には最大化できない。迷ったらリファクタリング耐性を優先する。**
偽陽性（壊れていないのに赤い）は偽陰性より高くつく — 赤が信用されなくなった時点で、
残り3つの柱がまとめて意味を失うため。テストが**内部構造を知らないこと**が、
そのまま「実装を書き換えてよい自由」になる。

## 2. 古典派をとる

**テストの単位は「クラス」ではなく「振る舞いの1単位」。** 1つの振る舞いを確かめるのに
複数のオブジェクトが協力するなら、**協力させたまま**テストしてよい。
`MealCoverageService` のテストで本物の `Meal` と本物の `StockItem` を使うのが正しい。

| 依存の種類 | 例 | 扱い |
| --- | --- | --- |
| 内部の協力オブジェクト | エンティティ・値オブジェクト・ドメインサービス | **本物を使う。** ダブルにしない |
| 不変依存 | 純粋関数、定数 | **本物を使う** |
| プロセス外の共有依存 | Supabase、LLM API | **記憶上の実装（fake）に差し替える。** ポートの背後にある（ADR-002 / ADR-005） |

**`vi.mock` と `vi.fn()` による「呼ばれたか」の検証を既定で使わない。** 呼び出しの順序や
回数は実装の都合であり、振る舞いではない。差し替えが要るところは
**インターフェースの記憶上の実装**を書く — 型が合っていることまで一緒に確かめられる。

**例外は「呼ばないこと自体が仕様」のときだけ。** C-7（在庫が変わらなければ再生成しない）と
C-15（再利用が成立したら LLM を呼ばない）は、外部への呼び出しが**起きないこと**が
要件そのものである。このときも `vi.fn()` ではなく、**記憶上の実装に呼び出し回数を持たせ、
状態として検証する。**

```ts
const 生成器 = 記憶上の献立生成器({ 返す献立: [...] });
// ...実行...
expect(生成器.呼ばれた回数).toBe(0); // C-15: 再利用が成立したら生成しない
```

## 3. 観察可能な振る舞いと実装詳細

**公開 API を通して外から見えるものだけを検証する。**

| 観察可能な振る舞い（検証してよい） | 実装詳細（検証しない） |
| --- | --- |
| 戻り値・DTO の中身 | private メソッド、内部のヘルパー関数 |
| 投げる例外の**型**と識別子 | 例外の文言そのもの |
| リポジトリに保存された結果（次の取得で見える） | 保存が何回呼ばれたか、どのSQLか |
| 決定的な並び順（C-12） | 並び替えのアルゴリズム |
| 呼び出しが**起きないこと**が要件のもの（C-7 / C-15） | それ以外の呼び出し回数 |

見分け方は1つ。**「実装を別の書き方に置き換えたとき、このテストは赤くなるか」。**
振る舞いが同じなのに赤くなるなら、それは実装詳細を握っている。

具体的に守ること:

- **テストのためだけの公開メソッド・getter を本体に足さない。** 見えないものは、
  見える振る舞いを通して確かめる（保存したなら、取得して確かめる）
- **期待値に計算式を書かない。** 実装と同じ式をテストに書くと、式が間違っているときに
  両方が同じだけ間違う。**期待値は literal で置く**
- **1つのテストで検証する振る舞いは1つ。** 「登録できる」と「一覧に出る」は別のテスト

## 4. 層ごとの方針

| 層 | 何を確かめるか | ダブル |
| --- | --- | --- |
| `domain/` | 不変条件、値の正規化、ドメインサービスの結果と**並び順** | **不要。** 副作用も永続化も持たない（`docs/domain-model.md` 4章） |
| `usecase/` | ユースケース1件の入出力と、実行後に**リポジトリから見える状態** | リポジトリとポートのみ、記憶上の実装で |
| `infrastructure/` | 腐敗防止層の**変換と検証**（LLM 応答 → `Meal`、通らない応答を弾くこと。ADR-005） | HTTP は呼ばない。**応答の文字列を入力として渡す** |
| `api/` | ルーティングと DTO の受け渡し。ドメインの型が漏れていないこと | ユースケースを差し替える |
| `apps/web` | 表示の分岐と入力の扱い。**画面は API のクライアントであり、ユースケースを直接呼ばない**（ADR-003） | API クライアントを差し替える |
| `.claude/hooks` `.githooks` | ガードの**拒否側と許可側の両方**。`pnpm test:hooks`（`node --test`） | なし |

**ドメイン層とユースケース層のテストは、実 DB も実 API も使わずに書ける**（ADR-002）。
**それを実際に使うテストは `pnpm test` に入れない。** 実 DB に対するテスト（RLS の回帰・
リポジトリ実装）は **`apps/api/test/db/**` に置き、`pnpm test:db` で走らせる。** 相手は
**ローカル Postgres（Docker Compose）であって実 Supabase ではない** — 実 Supabase を要した頃は
ローカルでも CI でも回せなかった（ADR-029）。`pnpm test` 側は `apps/api/test/db/**` を
`exclude` するので、**同じテストが2度走らない。**

**RLS のポリシーには、振る舞いからは観察できないものがある。** `select` のポリシーが先に効くため、
`update` / `delete` が `where` で行を指す以上、その行はまず `select` を通らないと走査に載らない。
4本の述語が `household_id = (select auth.uid())` で揃っている以上、**「`select` は通るが `update` の
`using` で弾かれる」入力が存在しない。** 実際、`stock_items` で `update` の `using` / `with check` と
`delete` の `using` をそれぞれ `true` に緩めても、**振る舞いのテストは1件も落ちなかった**（2026-09-10 の
変異テスト。B-07b）。これらは**多重防御であって、アプリの入口からは効きが見えない。**

そこで **`pg_policies` に実際に入っている述語を突き合わせる** — `update` / `delete` の述語が
`select` / `insert` のそれと同一であることを見る。**述語の文字列を期待値に書かない**（Postgres が
正規化した形は版で変わる）。同じ正規化を通った者どうしを比べ、**引き当ては `policyname` ではなく
`cmd` で行う**（改名で「理由の読めない赤」にしない）。表が増えるたびに同じことが要る。

**新しいポリシーを足したら、1本ずつ `true` に緩めて回す。** 落ちないポリシーは、
**守られていないのと同じである。**

**Docker が使えない環境でも、まず `pnpm db:up:native` を試す**（ADR-030）。素の PostgreSQL を
55432 に立てるだけで、compose と同じ役と `auth.uid()` が入る。エージェントのコンテナでは
セッション開始のフックが自動で立てるので、**そのまま `pnpm test:db` が回る。**
**それも駄目なときに限り、赤も緑も CI の結果で確かめる** — ドラフト PR を push し、
期待した理由で落ちていることをログで見てから実装に入る（ADR-029 の結果6）。**緑を装わない。**

**ローカルは 16、CI と compose は 17。** ローカルは手元の速い経路であって、**正は CI である**
（ADR-030 の結果1）。とくに上の `pg_policies` の突き合わせのように**版で結果が変わりうる検証は、
17 の結果をもって判断する。**

**画面のテストはフラグを介さない。** feature flag があるのは `apps/web` だけで、
ユースケース層とドメイン層はそれを知らないため（ADR-024）、フラグの有無に関わらず
検証は成立する。**画面に到達できないことと、検証されていないことは別である**
（`docs/workflow.md` 1章）。

## 5. 速さを担保する

**`pnpm test` は数秒で返る。** 遅いテストは書かれた回数だけ実行されなくなる。

**禁止:**

| 禁止 | 代わりに |
| --- | --- |
| `sleep` / 実時間の待ち | 待たない設計にする |
| ネットワーク・DB・ファイルシステム | 記憶上の実装 |
| `new Date()` / `Date.now()` を本体が直接読む | **時刻は引数で渡す。** テストは固定値を渡す |
| `crypto.randomUUID()` を本体が直接読む | **識別子は引数で渡す**（`createStockItem` は `id` を受け取っている） |
| 巨大なテストデータの生成 | 振る舞いの確認に要る最小の件数（多くは2〜3件） |

**リポジトリ内のファイルを読むテストは例外**（マイグレーションに RLS が同居していることの守り等）。
**対象がファイルの中身そのもの**であり、数 KB の同期読みは決定的で数ミリ秒に収まる。禁止の趣旨は
プロセス外の共有依存による遅さと非決定性であって、そこには当たらない。

**現在時刻と乱数を本体の中で読むと、テストが遅いのではなく決定的でなくなる。**
引数で受け取る形で足りなくなったら、**ポートを起こす前に `docs/adr.md` に ADR を提案する** —
ポートを増やすのは設計の決定であり、テストの都合で決めてよいものではない（ADR-002）。
期限の残日数（FR-11）も、再利用の並び（C-12）も、**基準時刻を渡して**確かめる。

## 6. 書き方

**配置** — `src/` の構造を `test/` に写す。

```
apps/api/src/contexts/pantry/domain/entity/StockItem.ts
apps/api/test/contexts/pantry/domain/StockItem.test.ts
```

**共有する道具は `apps/api/test/support/<コンテキスト>/` に置く。** 記憶上のリポジトリのように、
複数のテストが同じものを使うヘルパーの置き場である。`src/` に置くと Worker の成果物に載り、
`infrastructure/` に置くと本物の実装と並んで**結線を間違えたときに気づけない**。
`test/contexts/**` は `src/` の写しなので、src に対応の無いものをそこに混ぜない。
vitest が拾うのは `.test.ts` だけなので、ここに置いたものは収集されない。

**命名** — `describe` は対象（`在庫品 StockItem`）、`it` は**振る舞いを日本語の文**で書く。
「〜する」「〜を許さない」。`it('should work')` のような、落ちたときに何が壊れたか
わからない名前を書かない。

**構造** — 準備・実行・検証の3つに分ける。空行で区切れば十分で、コメントで
`// Arrange` と書く必要はない。

**ヘルパー** — テストの本題でない値はヘルパー関数に隠す。**本題だけが `overrides` に現れる**形にする。

```ts
function 在庫品(overrides: Partial<...> = {}) { ... }

it('名称の前後の空白は落とす', () => {
  expect(在庫品({ name: '  にんじん  ' }).name).toBe('にんじん');
});
```

**根拠のコメント** — 「なぜこの振る舞いなのか」が要件・確定事項に由来するときは、
**その番号を書く**（`// C-6: 充足判定は名称の完全一致`）。番号のないルールは、次の実装者が
消してよいものだと判断する。

**例外を期待するときは型を指定する。**

```ts
expect(() => 在庫品({ name: '' })).toThrow(PantryRuleViolation);
```

`toThrow()` を引数なしで書かない。未実装のスタブ（`throw new Error('未実装')`）でも
緑になってしまい、**赤を確認する工程が意味を失う。**

## 7. 禁止

- **テストを `skip`・無効化・削除して緑にしない**（`docs/workflow.md` 第2章）
- **実装に合わせてテストを書き換えない。** 仕様が変わったときだけテストを変える。
  そのときは**なぜ変えたかをコミットメッセージに書く**
- **カバレッジの数値を目標にしない。** 確かめたいのは行が通ったことではなく振る舞い
- **スナップショットテストを既定にしない。** 何が壊れたか読めず、赤を機械的に更新しがちなため
- **用語表にない語をテストコードに書かない**（`docs/domain-model.md` 第3章）。テストも `pnpm lint` の対象

## 8. TDD の1周

```
テストケースの洗い出し → テストの実装（赤） → 実装（緑） → リファクタ（緑のまま）
```

| 段 | 担当 | 出るもの | 触ってよいもの |
| --- | --- | --- | --- |
| 洗い出し | `test-designer` | テストケース一覧（根拠つき） | **何も書かない** |
| 赤 | `test-writer` | テストコード。**落ちることを確認済み** | `test/**` と、署名だけのスタブ |
| 緑 | `implementer` | 実装。`pnpm verify` が緑 | `src/**`。**テストは変えない** |

**赤を飛ばさない。** 落ちることを見ていないテストは、通ることを確かめていないのと同じである
（条件を間違えて常に緑のテストは、書いた瞬間から何も守らない）。

**テストを書く者と実装する者を分ける**のは、実装の都合がテストに入り込むのを
構造的に止めるため。`implementer` がテストを変えたくなったら、**それは仕様の問題なので止まる**。
