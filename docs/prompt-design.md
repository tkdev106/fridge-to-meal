# 献立生成のプロンプト設計

> ドラフト v0.3 / 2026-09-07 / 要件定義書 v0.6・ドメインモデル v0.3・ADR-001〜022 に対応
> v0.3: ADR-022（再利用と生成を混ぜない）を反映。論点2 は前提が消えて解消。
> v0.2: 第12章の論点1・3・4・5 に判断を得て反映。
> 閲覧用 HTML は未作成。**この Markdown が正である。**

`MealGenerator` ポート（ADR-002）を LLM で実装するにあたり、**何を渡し、何を返させ、何を受け取らないか**を定める。プロンプトの文字列そのものと、その検証規則を含む。

**この文書の内容が置かれる場所は `apps/api/src/contexts/meal/infrastructure/` である。** ドメイン層とユースケース層には、ここに書かれた文字列も JSON もモデル名も現れてはならない（ADR-005）。

---

## 1. この文書が決めること・決めないこと

| | 内容 |
| --- | --- |
| **決める** | ポートの入出力契約、システムプロンプト全文、ユーザーメッセージの組み立て方、応答 JSON の形式と検証規則、呼び出しパラメータ、失敗時の扱い |
| **決める** | 試行に使う在庫パターンと、評価の観点・記録様式 |
| **決めない** | LLM プロバイダとモデル（ADR-019。**この設計はプロバイダ非依存に書く**） |
| **決めない** | 実測されたトークン数と費用（第10章に手順だけ置く。**試行を実施した人が埋める**） |
| **差し戻す** | 未決事項に接続する論点は第12章。**5件すべて決着済み**（4件は判断を得て決定、1件は ADR-022 により前提が消滅） |

## 2. ポートの契約

`MealGenerator` はドメイン層のインターフェース（ADR-002）。**ドメインの語彙だけで定義し、プロンプトも JSON もここには現れない。**

### 2.1 入力

| 項目 | 型 | 内容 |
| --- | --- | --- |
| `pantrySnapshot` | `PantrySnapshot` | 生成時点の在庫の複製 |
| `requiredCount` | `3` | 生成する件数。**ADR-022 により常に3である** — 生成が起きるのは提案全体を生成するときだけで、再利用で埋まった残りを生成することはない |
| `avoidTitles` | `string[]` | 避けるべき献立の名称。上限50件（ADR-021） |
| `asOf` | `DateTime` | 期限の残日数を算出する基準日 |

`householdId` は渡さない。**世帯の識別は生成の関心事ではない**うえ、外部に送る情報を最小にする（NFR-11）。

`requiredCount` は当面つねに3だが、**ポートの引数としては残す**。ADR-021 が定めた「在庫スナップショット・必要件数・避けるべき献立名」という契約であり、件数を呼ぶ側の判断として持たせておく形は変えない。

### 2.2 出力

検証を通過した献立だけを返す。`Meal` そのものではなく、`MealId` と `householdId` を持たない生成結果として返し、永続化はユースケース層が行う（C-1）。

```
GeneratedMeal {
  title: string
  ingredients: { name: string, amount: string }[]
  steps: string[]   // 添字が順序
}
```

`provenance` は常に `'llm'` なので、ポートの戻り値には含めず、`Meal` を組み立てる側で付与する。

### 2.3 外部に送らないもの（NFR-11）

**送るのは在庫品の `name` / `amount` / 期限の残日数と、避けるべき献立の名称だけ。** 以下は一切送らない。

`householdId` / `userId` / メールアドレス / `StockItemId` / `MealId` / 登録日時 / 調理記録 / 在庫の登録経路

> **在庫スナップショットと、プロンプトに載せる在庫は別物である。** スナップショットは C-7 の同一性判定のために全件を保持する。プロンプトに載せるのはそこからの射影であり、第3章 D-5 の通り一部を落とす。

## 3. プロンプト設計の前提となる6つの決定

プロンプト本文より先に、なぜその書き方になるかを決める。**ここを読まずに本文だけ書き換えると、ADR-017 の再利用が働かなくなる。**

### D-1　常備調味料を材料に含めさせない　⚠ 最重要

**理由: これを守らないと ADR-017（再利用による LLM 呼び出しの削減）が成立しない。**

充足判定は食材名の完全一致で行う（C-6）。`MealIngredient` に「醤油」「サラダ油」が含まれると、冷蔵庫の在庫として登録されていない限り**必ず不足材料になる**。すると:

- `CookableMeal`（不足0件）が**ほぼ永久に0件**になる（C-10）
- 再利用が発動せず、毎回 LLM を呼ぶ（ADR-017 の削減効果が丸ごと消える）
- FR-17 の不足材料一覧が調味料で埋まり、本当に足りない食材が埋もれる

したがって**常備調味料は材料に書かせず、手順の中に分量とともに書かせる**。プロンプトで列挙して固定する。

```
塩、こしょう、砂糖、醤油、味噌、酢、みりん、酒、サラダ油、ごま油、
片栗粉、小麦粉、だしの素、コンソメ、鶏がらスープの素、マヨネーズ、ケチャップ、バター
```

| 引き受ける代償 | 対処 |
| --- | --- |
| 材料一覧を見ただけでは調味料の要否が分からない | 手順に必ず分量を書かせる（システムプロンプト 規則5） |
| このリストにない調味料（オイスターソース等）は不足材料として出る | **正しい挙動である。** 常備を前提にできないものは不足として見せてよい |
| 利用者が醤油を在庫として登録していると、材料に現れず在庫と結びつかない | 充足判定は「材料→在庫」の方向なので害はない。在庫側に余るだけ |

> **このリストはプロンプト側に置き続ける（決定済み。第12章 論点3）。** 食材カタログに調味料を載せない方針のため、カタログ由来にはしない。
>
> 利用者が調味料を在庫として登録すること自体は妨げない。ただしカタログにないため、FR-02 の入力サジェストには出ず、自由入力（FR-03）になる。**献立の提案には影響しない** — D-1 により材料に現れないためである。

### D-2　期限は日付ではなく残日数に変換して渡す

LLM に日付の計算をさせない。`asOf` と `expiryDate` から残日数をインフラ層で算出し、文言にして渡す。

| 残日数 | 文言 |
| --- | --- |
| 0 | `期限は今日` |
| 1〜7 | `期限まであとN日` |
| 8以上 | `期限に余裕あり` |
| 未設定 | （期限を書かない） |

8日以上をまとめるのは、そこから先は献立の選択に影響しないため。**残日数の桁を上げても提案は変わらず、トークンだけ増える。**

### D-3　材料名は在庫の表記をそのまま使わせる

C-6 の完全一致を通すための、最も効く一手。在庫が「豚こま肉」なら材料名も「豚こま肉」でなければならず、「豚肉」「豚こま」に言い換えられた時点で不足材料になる。

**在庫にある食材を使うときは表記を変えないことを、規則として明示する。** 在庫にない食材（追加購入分）は一般的な名称で書かせる。

> 食材カタログの別名データ（Q-4）は、この規則を破られたときの受け皿である。**まずプロンプトで守らせ、漏れをカタログで拾う**という二段構えにする。

### D-4　充足判定を LLM にさせない

FR-17 の「賄える材料 / 不足材料」は `MealCoverageService` が算出する（ADR-009、C-6）。**LLM に判定させると、ドメインの判定と食い違ったものが画面に出る。**

したがって応答 JSON に `available` `missing` `不足` に相当するフィールドを置かない。LLM は献立を出すだけで、その献立が今日作れるかを判断しない。

### D-5　期限を過ぎた在庫はプロンプトに載せない

安全側に倒す。期限切れの食材を使う献立を提示することは、FR-20 の注意表示で吸収できる範囲を超える。

- 在庫一覧には残る（FR-12 の「当日/超過=危険」表示）。**消えるのはプロンプトからだけ。**
- C-7 の在庫スナップショット比較には期限切れの在庫も含める。落とすのはプロンプトへの射影のみ。
- 在庫が全件期限切れの場合、プロンプトに載る在庫が0件になる。**この場合は LLM を呼ばず、在庫の更新を促す**（第8章）。

### D-6　避けるべき献立名の先頭は「直前に提示した献立」

ADR-021 が挙げるのは既存の献立名だが、順序が要る。**生成が起きる場面のうち片方は、利用者が新しい献立を明示的に求めたときである**（FR-36 / ADR-022）。そこで直前に見ていたものが出ては、要求に応えていない。

```
avoidTitles = 直前の提案に含まれていた献立の名称（1〜3件）
            + 直近の献立の名称（生成日時の新しい順）
            合計50件を上限とし、超えた分は古いものから捨てる
```

直前の提案分を先頭に置いて上限で切ることで、**最も出てはいけないものが必ず残る。** 蓄積が50件を超えても、直前に見た献立だけは確実に避ける対象に入る。

> **ADR-022 により、再利用と生成は同じ提案に同居しない。** したがって「今回すでに採用した献立との衝突」は起こらず、避けるべきは*直前の*提案の献立である。

## 4. システムプロンプト（全文）

固定文字列。在庫にも件数にも依存しない。

```text
あなたは日本の家庭の食事を組み立てる調理の専門家です。
冷蔵庫にある食材の一覧を受け取り、その食材で作れる家庭向けの献立を提案します。

# 守ること

1. 指定された JSON だけを出力する。前置き、説明、コードブロックの記号を書かない。
2. 1件の献立は主菜1品とする。副菜や汁物をまとめて1件にしない。分量は2人分とする。
3. 材料には、在庫にある食材を優先して使う。在庫にない食材を足してよいのは
   1件の献立につき2つまでとする。
4. 在庫にある食材を材料に書くときは、在庫に書かれている名称をそのまま使う。
   「豚こま肉」を「豚肉」や「豚こま」に書き換えない。
5. 次の常備調味料は材料に書かない。手順の中に分量とともに書く。
   塩、こしょう、砂糖、醤油、味噌、酢、みりん、酒、サラダ油、ごま油、
   片栗粉、小麦粉、だしの素、コンソメ、鶏がらスープの素、マヨネーズ、ケチャップ、バター
   ここに挙げていない調味料（オイスターソース、豆板醤など）は材料に書く。
6. 期限が近い食材を優先して使う。「期限は今日」「期限まであと1日」と書かれた
   食材がある場合、少なくとも1件の献立でそれを主な材料として使う。
7. 調理時間は40分以内、手順は6ステップ以内に収める。
   1ステップは60字以内で、一続きの作業を1文で書く。
8. 「避けたい献立」に挙げられたものを提案しない。名称の書き方が違っても、
   同じ食材を同じ調理法で扱うものは同じ献立とみなして避ける。
   例:「豚肉と白菜の炒め物」と「豚こまと白菜の中華炒め」は同じ。
9. 複数件を提案するときは、互いに調理法を変える。
   炒める・煮る・焼く・蒸す・和える・揚げるが重ならないようにする。
10. 肉・魚・卵は必ず十分に加熱する手順を書き、加熱の目安時間を添える。
    確信のない分量や加熱時間を書かない。書けない場合は別の献立にする。
11. 名称は30字以内で、主な食材と調理法が分かるものにする。

# 出力する JSON の形式

{
  "meals": [
    {
      "title": "献立の名称",
      "ingredients": [
        { "name": "食材名", "amount": "分量" }
      ],
      "steps": [
        "手順1", "手順2"
      ]
    }
  ]
}

meals の件数は、指示された件数と正確に一致させる。
ingredients は1件以上10件以内、steps は3件以上6件以内とする。
amount は「200g」「1/4個」「大さじ2」のような文字列にする。
上記以外のフィールドを追加しない。
```

### 各規則が担っている要件

| 規則 | 根拠 |
| --- | --- |
| 1 | ADR-005（ACL が解析できる形式） |
| 2 | 分量は2人分に固定する（MVP）。**将来、世帯の人数に合わせて選べるようにする**（要件定義 第10章。決定済み、第12章 論点5） |
| 3 | FR-16。在庫起点であることの担保。追加2件までは FR-17 の不足材料が過大にならない上限 |
| 4 | **D-3**。C-6 の完全一致を通す |
| 5 | **D-1**。ADR-017 の成立条件 |
| 6 | FR-18 |
| 7 | NFR-C3（出力トークンの抑制） |
| 8 | FR-42 / ADR-021 |
| 9 | FR-16 の「複数件」が意味を持つための条件。3件が全部炒め物では選べない |
| 10 | FR-20。注意表示だけに頼らず、生成側でも安全側に寄せる |
| 11 | C-4 の名称完全一致による既存参照が働く程度に、名称を安定させる |

## 5. ユーザーメッセージ

在庫・件数・避けたい献立から組み立てる。**トークンを抑えるため表組みを使わず、1行1件の素朴な列挙にする。**

### 5.1 テンプレート

```text
# 今日の在庫

{在庫行の並び}

# 提案してほしい件数

{requiredCount}件

# 避けたい献立

{避けたい献立の名称の並び}
```

- 在庫行は `- {name} {amount} {期限文言}`。`amount` が未設定なら分量を書かない。期限文言は D-2 の表による。
- **在庫は期限の近い順に並べる。** FR-04 の既定ソートと同じ並びであり、規則6を並び順でも補強する。期限未設定の在庫は末尾に置く。
- 避けたい献立が0件のときは、この節ごと出力しない。**空の見出しは無意味なトークンである。**

### 5.2 組み立て例

在庫8件・生成2件・避けたい献立3件の場合。

```text
# 今日の在庫

- 豚こま肉 300g 期限は今日
- 白菜 1/4個 期限まであと2日
- 絹ごし豆腐 1丁 期限まであと3日
- 卵 4個 期限まであと6日
- にんじん 2本 期限に余裕あり
- 玉ねぎ 3個 期限に余裕あり
- じゃがいも 4個 期限に余裕あり
- 乾燥わかめ

# 提案してほしい件数

2件

# 避けたい献立

- 豚こま肉と白菜のうま煮
- 鶏むね肉となすの照り焼き
- じゃがいもと玉ねぎのそぼろ煮
```

### 5.3 期待する応答

```json
{
  "meals": [
    {
      "title": "豚こま肉と白菜の生姜焼き",
      "ingredients": [
        { "name": "豚こま肉", "amount": "300g" },
        { "name": "白菜", "amount": "1/4個" },
        { "name": "玉ねぎ", "amount": "1個" },
        { "name": "しょうが", "amount": "1かけ" }
      ],
      "steps": [
        "白菜を一口大、玉ねぎを薄切りにし、しょうがをすりおろす。",
        "醤油大さじ2、みりん大さじ2、酒大さじ1、すりおろしたしょうがを混ぜる。",
        "フライパンにサラダ油を熱し、豚こま肉を色が変わるまで3分ほど炒める。",
        "玉ねぎと白菜を加えて5分ほど炒め、しんなりしたら調味料を加える。",
        "汁気が少なくなるまで2分ほど煮からめる。"
      ]
    },
    {
      "title": "絹ごし豆腐とにんじんの卵とじ",
      "ingredients": [
        { "name": "絹ごし豆腐", "amount": "1丁" },
        { "name": "にんじん", "amount": "1本" },
        { "name": "卵", "amount": "2個" }
      ],
      "steps": [
        "にんじんを細切りにし、絹ごし豆腐を水切りして角切りにする。",
        "鍋にだしの素小さじ1と水200mlを入れ、にんじんを5分煮る。",
        "醤油大さじ1とみりん大さじ1を加え、豆腐を入れて3分煮る。",
        "溶き卵を回し入れ、蓋をして卵に完全に火が通るまで2分加熱する。"
      ]
    }
  ]
}
```

**この応答が満たしていること:** 醤油・みりん・だしの素が材料に現れない（D-1）／在庫の表記「豚こま肉」「絹ごし豆腐」がそのまま使われている（D-3）／期限が今日の豚こま肉が1件目の主材料になっている（FR-18）／炒めると煮るで調理法が分かれている（規則9）／卵に完全に火を通す手順がある（FR-20）。

**在庫にない「しょうが」が1件だけ追加されている。** これは規則3の範囲内であり、FR-17 では不足材料として表示される。

## 6. 応答の検証規則（腐敗防止層）

`MealResponseParser` の責務（ADR-005）。**ここを通らなかったものはドメイン層に渡らない。**

### 6.1 段階

| 段階 | 内容 | 失敗時 |
| --- | --- | --- |
| 1. 抽出 | 応答文字列から JSON 部分を取り出す。コードブロックの記号や前置きが付いていても、最初の `{` から対応する `}` までを取る | 失敗 |
| 2. 構文 | JSON として解析する | 失敗 |
| 3. 構造 | `meals` が配列であること | 失敗 |
| 4. 件数 | 下表の通り | 下表の通り |
| 5. 各献立の検証 | 下表の通り。**1件でも通らなければその献立だけを捨てる** | 件数の再判定へ |
| 6. 正規化 | 下表の通り | — |

規則1で「コードブロックの記号を書かない」と指示していても段階1を実装するのは、**指示の遵守を前提にした解析が最も壊れやすい**ため。指示は出力トークンの節約として意味があり、解析の保証としては当てにしない。

### 6.2 献立ごとの検証

| 項目 | 規則 | 違反時 |
| --- | --- | --- |
| `title` | 文字列。前後の空白を除いて1文字以上、40字以内 | 献立を捨てる |
| `title` | 同じ応答内で重複しない | 後に出たものを捨てる |
| `title` | **直前の提案に含まれていた献立の名称**と完全一致しない | 献立を捨てる（FR-36。新しさを求めた操作で同じものを返さない） |
| `ingredients` | 配列。1件以上10件以内 | 献立を捨てる |
| `ingredients[].name` | 文字列。1文字以上30字以内 | その材料を捨てる |
| `ingredients[].amount` | 文字列。0文字を許し、その場合は分量なしとする。30字以内 | 空文字に丸める |
| `steps` | 配列。1件以上8件以内 | 献立を捨てる |
| `steps[]` | 文字列。1文字以上150字以内 | その手順を捨てる |
| 余分なフィールド | 無視する | — |

`title` 40字・`steps` 8件・150字は、**プロンプトの指示（30字・6件・60字）より緩い。** 指示は出力を短く保つためのもので、検証は壊れていないものを落とさないためのもの。役割が違うので値を揃えない。

### 6.3 正規化

| 対象 | 処理 |
| --- | --- |
| 全文字列 | 前後の空白を除去 |
| `ingredients[].name` | **常備調味料リスト（D-1）に完全一致するものを除去する** |
| `ingredients` | 除去の結果0件になったら、その献立を捨てる |
| `ingredients` | 同じ `name` が複数あれば最初の1件だけ残す |
| `steps` | 除去の結果0件になったら、その献立を捨てる（`Meal` の不変条件） |

材料からの調味料除去を検証側にも置くのは、**D-1 が守られなかったときに再利用の仕組みが静かに壊れる**ため。プロンプトの遵守に依存させない。

### 6.4 件数の扱い

| 状況 | 扱い |
| --- | --- |
| 検証を通った献立が `requiredCount` より多い | **先頭から `requiredCount` 件を採用する。** 余りは捨て、保存もしない（C-1 は「提示する献立を保存する」であって、捨てたものは献立ではない） |
| ちょうど `requiredCount` 件 | 採用 |
| 1件以上だが `requiredCount` 未満 | **失敗として扱う。** 提案は「ちょうど3件」が不変条件のため成立しない。6.5 と同じ経路でユーザーに再試行を促す（NFR-07）。採用した献立は保存しない（決定済み。第12章 論点1） |
| 0件 | 失敗として扱う |

### 6.5 失敗時

ADR-005 の通り、**自動リトライは行わない。** ユーザーに再試行の手段を提示する（NFR-07）。

- 生成の失敗は在庫の閲覧・保存済みの献立の閲覧に影響しない（NFR-06）
- 失敗した応答は保存しない（C-1 の裏返し）
- 失敗の回数は NFR-C2 の1日の生成回数に**数える**。数えないと、失敗を繰り返す経路が上限を素通りする

## 7. 呼び出しパラメータ

プロバイダ非依存の意図として記す。名称は各社の API に読み替える。

| 項目 | 値 | 理由 |
| --- | --- | --- |
| 温度 | 高め（1.0 相当） | 明示的な再生成で違う献立が出ることが要件（FR-36 の意図）。低くすると同じ在庫で同じものばかりになる |
| 最大出力トークン | 2048 | 3件分の上限（第10章の見積り）に余裕を持たせた値。**打ち切りは JSON 破損として現れる**ため、切り詰めすぎない |
| 構造化出力の強制 | プロバイダの機能があれば使う | ADR-019 の比較軸(1)。**ただし使えても第6章の検証は省かない** |
| 応答の先頭を `{` に固定する手法 | 使えるなら試す | 前置きの出力を抑え、出力トークンが減る。プロバイダ依存のため比較表（第11章）に記録する |
| プロンプトキャッシュ | **当面適用しない** | システムプロンプトは約900トークン（第10章）で、最小キャッシュ長に届かないモデルがある。NFR-C4 の注意点の通り、`cache_read_input_tokens` がゼロなら諦める |

**タイムアウトは Cloudflare Workers の制限に合わせる**（ADR-015）。生成が制限に収まらない場合、ストリーミングか非同期化への切り替えが必要になる。これは実装初期に測る（CLAUDE.md の必須事項）。

## 8. 生成を呼ばない条件

プロンプト設計の一部として、**そもそも投げない場合**を定める。

| 条件 | 扱い |
| --- | --- |
| プロンプトに載る在庫が0件（D-5 で全件落ちた場合を含む） | 呼ばない。在庫の登録・更新を促す |
| プロンプトに載る在庫が1件 | 呼ばない。**1食材で主菜3件は成立しない。** 在庫の追加を促す |
| **作れる既存の献立が1件以上ある** | 呼ばない。その1〜3件をそのまま提案とする（**ADR-022**。ここが最も効く経路） |
| 利用者が新しい献立を明示的に求めた | **呼ぶ。** 上の条件に優先する（FR-36）。この場合も下の在庫の条件は適用する |
| NFR-C2 の1日の上限に達している | 呼ばない。上限に達した旨を伝える |

在庫2件を境界にした理由: 2件あれば主菜が組める（例: 卵とにんじん）。1件は「ゆで卵」しか出ず、提案として無意味である。**この境界は試行（第9章 P-4）で見直す。**

## 9. 試行の設計

README の「これからやること 1」のうち、**プロバイダを決めずに実施できる部分**。以下のパターンで同一プロンプトを流し、第11章の表を埋める。

### 9.1 在庫パターン

| # | 名前 | 在庫 | 何を見るか |
| --- | --- | --- | --- |
| **P-1** | まとめ買い直後 | 20件。肉3・魚1・野菜8・卵乳3・豆腐等2・乾物3。期限は1〜10日に分散 | 基本形。3件の調理法が分かれるか（規則9）、材料名が在庫の表記のままか（D-3） |
| **P-2** | 週末前の残り物 | 5件。豚こま肉100g（期限は今日）・キャベツ1/4個・卵2個・にんじん1本・乾燥わかめ | **在庫が半端なときこそ本番**（要件 6.2 の案B採用理由）。追加食材が2件を超えないか |
| **P-3** | 極端に少ない | 2件。卵4個・玉ねぎ2個 | 第8章の境界。**3件生成させたときに無理な献立が出るか**、出るならどう不自然か |
| **P-4** | 期限が切迫 | 8件。うち3件が「期限は今日」（鶏むね肉・小松菜・木綿豆腐） | FR-18。切迫した3件が3件の献立に散るか、1件に集中するか |
| **P-5** | 蓄積後 | P-1 の在庫 + `avoidTitles` 50件（実在の献立名を想定した現実的な一覧） | **FR-42 の実効性とトークンの増分。** 50件が妥当か（Q-6）を判断する材料 |
| **P-6** | 偏った在庫 | 6件。野菜のみ（肉・魚・卵なし） | たんぱく質がない在庫で何を出すか。豆腐等を勝手に足さないか（規則3） |
| **P-7** | 表記ゆれを含む | P-2 の在庫の食材名を「豚こま」「キャベツ（1/4）」等の崩れた表記にする | D-3 が崩れた表記でも守られるか。**守られないなら食材カタログ（Q-4）の優先度が上がる** |

**各パターンを最低3回ずつ流す。** 温度が高いため1回では判断できない。

### 9.2 評価の観点

| 観点 | 測り方 | 満たすべき水準 |
| --- | --- | --- |
| **形式の妥当性** | 第6章の検証を通過した応答の割合 | **95%以上。** ADR-019 の比較軸(1)そのもの。ここが低いプロバイダは他が良くても採らない |
| **材料名の一致** | 在庫にある食材を使った材料のうち、在庫の表記と完全一致した割合 | **95%以上。** C-6 と ADR-017 に直結する |
| **調味料の混入** | 常備調味料リストの語が材料に現れた献立の割合 | **5%以下。** D-1 |
| **期限の遵守** | 「期限は今日」の食材が、3件のうち1件以上で主材料になった割合 | **90%以上。** FR-18 |
| **重複の回避** | `avoidTitles` と意味的に同じ献立が出た割合（**人が判定する**） | **10%以下。** FR-42 は努力目標なので0%を求めない |
| **調理法の分散** | 3件の調理法が3種類に分かれた割合 | 80%以上 |
| **不足材料の件数** | `MealCoverageService` 相当の判定を手で行い、不足材料の中央値を取る | **中央値1件以下。** 多いと FR-17 の表示が使い物にならない |
| **選べるか** | 「今日これを作るか」と自問して1件以上ある割合 | 2.2 の判断基準2。**数値ではなく所感を書く** |
| 入力トークン | 第10章 | — |
| 出力トークン | 第10章 | — |
| 応答時間 | 実測 | ADR-019 の比較軸(4)、ADR-015 の制限 |

### 9.3 記録の様式

パターン×試行回ごとに1行。**生の応答 JSON も残す。** 後からプロバイダを比べるとき、要約した数値だけでは判断できない。

```
| パターン | 回 | 検証 | 材料名一致 | 調味料混入 | 期限遵守 | 調理法 | 不足材料 | 入力tok | 出力tok | 秒 | 所感 |
```

## 10. 費用の実測

要件定義 6.3 の試算は概算である。**この設計が固まった今、実測に置き換える。**

### 10.1 手順

1. 第4章のシステムプロンプトと、第9章の各パターンから組み立てたユーザーメッセージを用意する
2. プロバイダのトークン計測 API（Claude なら `count_tokens`）で**入力**トークンを測る
3. 実際に生成を1回行い、応答の `usage` から**出力**トークンを読む
4. パターンごとに記録し、6.3 の表を更新する

### 10.2 設計時点の見積り

実測前の目安。**この数値を根拠に判断しないこと。**

| 部位 | 概算 |
| --- | --- |
| システムプロンプト（第4章） | 約900トークン |
| 在庫20件 | 約250トークン |
| 避けたい献立50件 | 約600トークン |
| 入力合計（P-5 相当） | **約1,800トークン** |
| 出力（3件・手順6ステップ） | **約1,000〜1,300トークン** |

**要件定義 6.3 の前提（入力1,000／出力2,000）とずれる。** 入力は避けたい献立の分だけ増え、出力は NFR-C3 の制約（手順6ステップ・60字）の分だけ減る。**費用の合計は概ね同じ桁**だが、内訳が違うので実測時に前提ごと書き換える。

### 10.3 プロンプトキャッシュの判断

システムプロンプトが約900トークンであることは、**NFR-C4 の注意点がそのまま当たる**ことを意味する。最小キャッシュ長が1024トークンを超えるモデルではキャッシュされない。

- 適用してみて `cache_read_input_tokens` がゼロなら**諦める**（NFR-C4 の指示通り）
- キャッシュのために意味のない文字列でシステムプロンプトを膨らませない。**入力トークンが増えて逆効果になる**

## 12. この設計から差し戻す論点

**勝手に決めずに、判断を仰ぐもの。**

### 論点1　生成が `requiredCount` に満たない場合　`決定済み`

**決定: 提案の組み立てごと失敗させ、ユーザーに再試行を促す。** 自動での再生成は行わない。

`Suggestion.entries` は「ちょうど3件」が不変条件のため、1〜2件しか検証を通らなければ提案は組めない。以下から選んだ。

| 案 | 内容 | 判断 |
| --- | --- | --- |
| **A** | 提案の組み立てごと失敗させ、再試行を促す | **採用。** ADR-005 の「自動リトライを行わない」と NFR-07 の「再試行の手段を提示する」に素直に乗る |
| B | 不足分だけ自動で再生成する | 不採用。待ち時間と費用が増え、ADR-005 と衝突する |
| C | `entries` を1〜3件に緩める | 不採用。不変条件の変更にあたり、FR-16 の「複数件」も崩れる |

実装上の帰結:

- 検証を通った1〜2件も**保存しない**。C-1 は「提示する献立を保存する」であり、提示しないものは献立ではない
- この失敗は NFR-C2 の1日の生成回数に**数える**（6.5 と同じ）
- 提案が3件固定であること自体（Q-3）は要件定義側の論点として開いたままだが、**本設計はそれを前提に閉じている**

> 発生頻度は P-3（在庫2件）と P-6（野菜のみ）の試行で測る。**頻発するなら案 C を含めて再考する**が、その判断材料が出るまでは A で進める。

> **ADR-022 で `Suggestion.entries` が「1件以上3件以下」に緩んだため、案 C の技術的な障壁は下がっている**（1〜2件の提案は再利用の経路ですでに起きる）。それでも A を維持するのは、**利用者が3件を求めて明示操作をした場面で1件だけ返すのは、要求に応えていない**ためである。再利用で1件になるのとは意味が違う。

### 論点2　C-13 と C-4 の衝突　`解消`

**ADR-022 により前提が消えた。C-4 への追記は不要。**

この論点は「同じ提案の中で、再利用した献立と生成した献立が同じ `Meal` を指しうる」という衝突だった。**ADR-022 で再利用と生成が同居しなくなったため、この経路は存在しない。**

生成のみの提案の中では、C-4 が同じ `mealId` を2度返すことはない — 応答内で `title` の重複を弾いており（6.2）、名称が異なれば参照先の既存の献立も異なるためである。

> 記録として残す。**組み立てを混ぜないという判断が、費用と体験のためだけでなく、不変条件を守る経路としても効いている。**

### 論点3　常備調味料リストの置き場所　`決定済み`

**決定: プロンプト側（D-1）に置き続ける。食材カタログには調味料を載せない。**

カタログ（Q-4）に調味料を含めない方針が確認されたため、二重管理は起きない。**D-1 のリストが調味料の唯一の定義である。**

| 帰結 | 内容 |
| --- | --- |
| カタログが未整備でも D-1 が働く | 再利用の仕組み（ADR-017）がカタログの整備状況に依存しなくなる。**この論点で最も価値のある結果** |
| 調味料は入力サジェストに出ない | FR-02 の補完対象外。在庫として登録したい場合は自由入力（FR-03）になる |
| FR-07 のカテゴリ「調味料」との関係 | カテゴリの選択肢としては残してよい。カタログに登録された食材の分類と、在庫の自由入力は別の話である |

### 論点4　`avoidTitles` の上限50件（Q-6 に接続）　`暫定で確定`

**決定: 50件のまま進める。ただし P-5 の試行で妥当性を測り、必要なら見直す。**

第10章の見積りでは、50件で入力トークンの約3分の1を占める。**削れるなら効果は小さくない**が、削って重複が増えれば FR-42 が形骸化する。

測り方は決まっている — P-5 で件数を **0 / 20 / 50** と変え、重複の回避率（9.2）と入力トークンの両方を記録する。**この3点が取れれば Q-6 は数字で閉じられる。**

### 論点5　分量を「2人分」に固定してよいか　`決定済み`

**決定: MVP は2人分に固定する。将来、選べるようにしてよい。**

要件定義の第10章（将来拡張）に「分量の選択」として記載した。MVP のスコープ外であり、**いま設定項目を作らない**（要件にない機能を足さない）。

将来これを入れるとき、プロンプト側で変わるのは第4章 規則2の一語だけである。**献立は生成時の分量のまま不変（C-3）**なので、設定を変えても過去の献立は変わらない。これは仕様として正しい — 履歴は生成時のまま残すべきものである（FR-30）。
