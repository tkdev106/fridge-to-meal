# 献立生成のプロンプト設計

> ドラフト v0.6 / 2026-09-07 / 要件定義書 v0.6・ドメインモデル v0.5・ADR-001〜023 に対応
> v0.6: D-1 を改訂。調味料を材料から外すのではなく、材料に種別を申告させる（ADR-023）。
> v0.5: 呼び出しパラメータを実際の API 仕様に合わせて訂正。試行ツールを `tools/prompt-trial/` に用意。
> v0.4: 論点1 を改訂。生成が3件に満たなくても、通った件数で提案を組む。
> v0.3: ADR-022（再利用と生成を混ぜない）を反映。論点2 は前提が消えて解消。
> v0.2: 第12章の論点1・3・4・5 に判断を得て反映。
> 閲覧用 HTML は未作成。**この Markdown が正である。**

`MealGenerator` ポート（ADR-002）を LLM で実装するにあたり、**何を渡し、何を返させ、何を受け取らないか**を定める。プロンプトの文字列そのものと、その検証規則を含む。

**この文書の内容が置かれる場所は `apps/api/src/contexts/meal/infrastructure/` である。** ドメイン層とユースケース層には、ここに書かれた文字列も JSON もモデル名も現れてはならない（ADR-005）。

## 1. この文書が決めること・決めないこと

| | 内容 |
| --- | --- |
| **決める** | ポートの入出力契約、システムプロンプト全文、ユーザーメッセージの組み立て方、応答 JSON の形式と検証規則、呼び出しパラメータ、失敗時の扱い |
| **決める** | 試行に使う在庫パターンと、評価の観点・記録様式 |
| **決めない** | LLM プロバイダとモデル（ADR-019。**この設計はプロバイダ非依存に書く**） |
| **決めない** | 実測されたトークン数と費用（第10章に手順だけ置く。**試行を実施した人が埋める**） |
| **差し戻す** | 未決事項に接続する論点は第12章。**4件は決定済み**（うち1件は ADR-022 により前提が消滅）、**論点4（`avoidTitles` の上限）は暫定で確定**し、試行の数字を待って閉じる |

## 2. ポートの契約

`MealGenerator` はドメイン層のインターフェース（ADR-002）。**ドメインの語彙だけで定義し、プロンプトも JSON もここには現れない。**

### 2.1 入力

| 項目 | 型 | 内容 |
| --- | --- | --- |
| `pantrySnapshot` | `PantrySnapshot` | 生成時点の在庫の複製 |
| `requiredCount` | `3` | 生成する件数。**ADR-022 により常に3である** — 生成が起きるのは提案全体を生成するときだけで、再利用で埋まった残りを生成することはない |
| `avoidTitles` | `string[]` | 避けるべき献立の名称。上限50件（ADR-021） |
| `asOf` | `DateTime` | 期限の残日数を算出する基準日 |

`householdId` は渡さない。**世帯の識別は生成の関心事ではない**うえ、外部に送る情報を最小にする（NFR-11）。

`requiredCount` は当面つねに3だが、**ポートの引数としては残す**。ADR-021 が定めた「在庫スナップショット・必要件数・避けるべき献立名」という契約であり、件数を呼ぶ側の判断として持たせておく形は変えない。

### 2.2 出力

検証を通過した献立だけを返す。`Meal` そのものではなく、`MealId` と `householdId` を持たない生成結果として返し、永続化はユースケース層が行う（C-1）。

```
GeneratedMeal {
  title: string
  ingredients: { name: string, amount: string, kind: 'main' | 'seasoning' }[]
  steps: string[]   // 添字が順序
}
```

`kind` は C-16 の材料の種別。**充足判定の対象を決めるのはこの値だけ**であり、ドメイン層はこれ以上の分類を知らない。

`provenance` は常に `'llm'` なので、ポートの戻り値には含めず、`Meal` を組み立てる側で付与する。

### 2.3 外部に送らないもの（NFR-11）

**送るのは在庫品の `name` / `amount` / 期限の残日数と、避けるべき献立の名称だけ。** 以下は一切送らない。

`householdId` / `userId` / メールアドレス / `StockItemId` / `MealId` / 登録日時 / 調理記録 / 在庫の登録経路

> **在庫スナップショットと、プロンプトに載せる在庫は別物である。** スナップショットは C-7 の同一性判定のために全件を保持する。プロンプトに載せるのはそこからの射影であり、第3章 D-5 の通り一部を落とす。

## 3. プロンプト設計の前提となる6つの決定

プロンプト本文より先に、なぜその書き方になるかを決める。**ここを読まずに本文だけ書き換えると、ADR-022 の再利用が働かなくなる。**

### D-1　材料に種別を申告させ、調味料を充足判定から外す　⚠ 最重要

**理由: これを守らないと ADR-017 / ADR-022（再利用による LLM 呼び出しの削減）が成立しない。**

充足判定は食材名の完全一致で行う（C-6）。`MealIngredient` に「醤油」「サラダ油」が含まれると、冷蔵庫の在庫として登録されていない限り**必ず不足材料になる**。すると:

- `CookableMeal`（不足0件）が**ほぼ永久に0件**になる（C-10）
- 再利用が発動せず、毎回 LLM を呼ぶ（ADR-017 / ADR-022 の削減効果が丸ごと消える）
- FR-17 の不足材料一覧が調味料で埋まり、本当に足りない食材が埋もれる

**回避の手段は「調味料を材料に書かせないこと」ではなく、「調味料を充足判定の対象から外すこと」である。** そこで材料ごとに種別を申告させる（ADR-023 / C-16）。

```json
{ "name": "豚こま肉",         "amount": "300g",   "kind": "main" }
{ "name": "オイスターソース",  "amount": "大さじ1", "kind": "seasoning" }
```

`MealCoverageService` は `main` だけを在庫と突き合わせる。**`seasoning` は賄えるものとしても不足するものとしても数えない。**

#### 固定リストは残す。ただし上限ではなく下限として

```
塩、こしょう、砂糖、醤油、味噌、酢、みりん、酒、サラダ油、ごま油、
片栗粉、小麦粉、だしの素、コンソメ、鶏がらスープの素、マヨネーズ、ケチャップ、バター
```

**このリストに載っているものは、種別が `main` と申告されていても `seasoning` に倒す**（6.3 の正規化）。逆は行わない — **リストにない調味料も `seasoning` として受け入れる。**

| | 現行の役割 |
| --- | --- |
| リストに載っている | **必ず**調味料として扱う（申告の誤りに対する保険） |
| リストに載っていない | 申告に従う。**オイスターソース・豆板醤・ナンプラーなども調味料になれる** |

**リストが調味料の集合を閉じないことが、この設計の要点である。**

| 引き受ける代償 | 対処 |
| --- | --- |
| 生成側の申告に依存する | **判別できない場合は `main` に倒す。** 不足材料が1件増えるだけで済む。逆に倒すと在庫にない食材が黙って判定から消える |
| 「バター」のように文脈で変わるものがある | どちらに倒れても影響は不足材料の1件の増減。**`CookableMeal` が壊滅する失敗モードよりはるかに軽い** |
| 出力トークンが増える | 材料ごとに数トークン。3件で数十トークンの規模であり無視してよい |

> **固定リストはプロンプト側に置き続ける（決定済み。第12章 論点3）。** 食材カタログに調味料を載せない方針のため、カタログ由来にはしない。
>
> 利用者が調味料を在庫として登録すること自体は妨げない。ただしカタログにないため、FR-02 の入力サジェストには出ず、自由入力（FR-03）になる。**献立の提案には影響しない** — 調味料は充足判定の対象外だからである。

### D-2　期限は日付ではなく残日数に変換して渡す

LLM に日付の計算をさせない。`asOf` と `expiryDate` から残日数をインフラ層で算出し、文言にして渡す。

| 残日数 | 文言 |
| --- | --- |
| 0 | `期限は今日` |
| 1〜7 | `期限まであとN日` |
| 8以上 | `期限に余裕あり` |
| 未設定 | （期限を書かない） |

8日以上をまとめるのは、そこから先は献立の選択に影響しないため。**残日数の桁を上げても提案は変わらず、トークンだけ増える。**

### D-3　材料名は在庫の表記をそのまま使わせる

C-6 の完全一致を通すための、最も効く一手。在庫が「豚こま肉」なら材料名も「豚こま肉」でなければならず、「豚肉」「豚こま」に言い換えられた時点で不足材料になる。

**在庫にある食材を使うときは表記を変えないことを、規則として明示する。** 在庫にない食材（追加購入分）は一般的な名称で書かせる。

> 食材カタログの別名データ（Q-4）は、この規則を破られたときの受け皿である。**まずプロンプトで守らせ、漏れをカタログで拾う**という二段構えにする。

### D-4　充足判定を LLM にさせない

FR-17 の「賄える材料 / 不足材料」は `MealCoverageService` が算出する（ADR-009、C-6）。**LLM に判定させると、ドメインの判定と食い違ったものが画面に出る。**

したがって応答 JSON に `available` `missing` `不足` に相当するフィールドを置かない。LLM は献立を出すだけで、その献立が今日作れるかを判断しない。

### D-5　期限を過ぎた在庫はプロンプトに載せない

安全側に倒す。期限切れの食材を使う献立を提示することは、FR-20 の注意表示で吸収できる範囲を超える。

- 在庫一覧には残る（FR-12 の「当日/超過=危険」表示）。**消えるのはプロンプトからだけ。**
- C-7 の在庫スナップショット比較には期限切れの在庫も含める。落とすのはプロンプトへの射影のみ。
- 在庫が全件期限切れの場合、プロンプトに載る在庫が0件になる。**この場合は LLM を呼ばず、在庫の更新を促す**（第8章）。

### D-6　避けるべき献立名の先頭は「直前に提示した献立」

ADR-021 が挙げるのは既存の献立名だが、順序が要る。**生成が起きる場面のうち片方は、利用者が新しい献立を明示的に求めたときである**（FR-36 / ADR-022）。そこで直前に見ていたものが出ては、要求に応えていない。

```
avoidTitles = 直前の提案に含まれていた献立の名称（1〜3件）
            + 直近の献立の名称（生成日時の新しい順）
            合計50件を上限とし、超えた分は古いものから捨てる
```

直前の提案分を先頭に置いて上限で切ることで、**最も出てはいけないものが必ず残る。** 蓄積が50件を超えても、直前に見た献立だけは確実に避ける対象に入る。

> **ADR-022 により、再利用と生成は同じ提案に同居しない。** したがって「今回すでに採用した献立との衝突」は起こらず、避けるべきは*直前の*提案の献立である。

## 4. システムプロンプト（全文）

固定文字列。在庫にも件数にも依存しない。

```text
あなたは日本の家庭の食事を組み立てる調理の専門家です。
冷蔵庫にある食材の一覧を受け取り、その食材で作れる家庭向けの献立を提案します。

# 守ること

1. 指定された JSON だけを出力する。前置き、説明、コードブロックの記号を書かない。
2. 1件の献立は主菜1品とする。副菜や汁物をまとめて1件にしない。分量は2人分とする。
3. 材料には、在庫にある食材を優先して使う。在庫にない食材を足してよいのは
   1件の献立につき2つまでとする。
4. 在庫にある食材を材料に書くときは、在庫に書かれている名称をそのまま使う。
   「豚こま肉」を「豚肉」や「豚こま」に書き換えない。
5. 材料には kind を必ず付ける。食材そのものは "main"、味付けに使うものは
   "seasoning" とする。
   "seasoning" にするもの: 塩、こしょう、砂糖、醤油、味噌、酢、みりん、酒、
   サラダ油、ごま油、片栗粉、小麦粉、だしの素、コンソメ、鶏がらスープの素、
   マヨネーズ、ケチャップ、バター、オイスターソース、豆板醤、ナンプラーなど、
   味や香りや口当たりをととのえるために少量使うもの。
   "main" にするもの: 肉、魚、野菜、卵、豆腐、乾物、麺、米など、
   その献立の中身になるもの。
   迷う場合は "main" にする。
6. 期限が近い食材を優先して使う。「期限は今日」「期限まであと1日」と書かれた
   食材がある場合、少なくとも1件の献立でそれを主な材料として使う。
7. 調理時間は40分以内、手順は6ステップ以内に収める。
   1ステップは60字以内で、一続きの作業を1文で書く。
8. 「避けたい献立」に挙げられたものを提案しない。名称の書き方が違っても、
   同じ食材を同じ調理法で扱うものは同じ献立とみなして避ける。
   例:「豚肉と白菜の炒め物」と「豚こまと白菜の中華炒め」は同じ。
9. 複数件を提案するときは、互いに調理法を変える。
   炒める・煮る・焼く・蒸す・和える・揚げるが重ならないようにする。
10. 肉・魚・卵は必ず十分に加熱する手順を書き、加熱の目安時間を添える。
    確信のない分量や加熱時間を書かない。書けない場合は別の献立にする。
11. 名称は30字以内で、主な食材と調理法が分かるものにする。

# 出力する JSON の形式

{
  "meals": [
    {
      "title": "献立の名称",
      "ingredients": [
        { "name": "食材名", "amount": "分量", "kind": "main" }
      ],
      "steps": [
        "手順1", "手順2"
      ]
    }
  ]
}

meals の件数は、指示された件数と正確に一致させる。
ingredients は1件以上12件以内で、"main" を1件以上含める。
steps は3件以上6件以内とする。
amount は「200g」「1/4個」「大さじ2」のような文字列にする。
kind は "main" か "seasoning" のどちらかとする。
上記以外のフィールドを追加しない。
```

### 各規則が担っている要件

| 規則 | 根拠 |
| --- | --- |
| 1 | ADR-005（ACL が解析できる形式） |
| 2 | 分量は2人分に固定する（MVP）。**将来、世帯の人数に合わせて選べるようにする**（要件定義 第10章。決定済み、第12章 論点5） |
| 3 | FR-16。在庫起点であることの担保。追加2件までは FR-17 の不足材料が過大にならない上限 |

| 6 | FR-18 |

| 8 | FR-42 / ADR-021 |

## 5. ユーザーメッセージ

在庫・件数・避けたい献立から組み立てる。**トークンを抑えるため表組みを使わず、1行1件の素朴な列挙にする。**

### 5.1 テンプレート

```text
# 今日の在庫

{在庫行の並び}

# 提案してほしい件数

{requiredCount}件

# 避けたい献立

{避けたい献立の名称の並び}
```

- 在庫行は `- {name} {amount} {期限文言}`。`amount` が未設定なら分量を書かない。期限文言は D-2 の表による。
- **在庫は期限の近い順に並べる。** FR-04 の既定ソートと同じ並びであり、規則6を並び順でも補強する。期限未設定の在庫は末尾に置く。
- 避けたい献立が0件のときは、この節ごと出力しない。**空の見出しは無意味なトークンである。**

### 5.2 組み立て例

在庫8件・生成3件・避けたい献立3件の場合。**生成は常に3件である**（2.1）。

```text
# 今日の在庫

- 豚こま肉 300g 期限は今日
- 白菜 1/4個 期限まであと2日
- 絹ごし豆腐 1丁 期限まであと3日
- 卵 4個 期限まであと6日
- にんじん 2本 期限に余裕あり
- 玉ねぎ 3個 期限に余裕あり
- じゃがいも 4個 期限に余裕あり
- 乾燥わかめ

# 提案してほしい件数

3件

# 避けたい献立

- 豚こま肉と白菜のうま煮
- 鶏むね肉となすの照り焼き
- じゃがいもと玉ねぎのそぼろ煮
```

### 5.3 期待する応答

**形式を示すのが目的なので、3件のうち2件だけを載せる。**

```json

    {
      "title": "豚こま肉と白菜の生姜焼き",
      "ingredients": [
        { "name": "豚こま肉", "amount": "300g", "kind": "main" },
        { "name": "白菜", "amount": "1/4個", "kind": "main" },
        { "name": "玉ねぎ", "amount": "1個", "kind": "main" },
        { "name": "しょうが", "amount": "1かけ", "kind": "main" },
        { "name": "醤油", "amount": "大さじ2", "kind": "seasoning" },
        { "name": "みりん", "amount": "大さじ2", "kind": "seasoning" }
      ],
      "steps": [
        "白菜を一口大、玉ねぎを薄切りにし、しょうがをすりおろす。",
        "醤油大さじ2、みりん大さじ2、酒大さじ1、すりおろしたしょうがを混ぜる。",
        "フライパンにサラダ油を熱し、豚こま肉を色が変わるまで3分ほど炒める。",
        "玉ねぎと白菜を加えて5分ほど炒め、しんなりしたら調味料を加える。",
        "汁気が少なくなるまで2分ほど煮からめる。"
      ]
    },
    {
      "title": "絹ごし豆腐とにんじんの卵とじ",
      "ingredients": [
        { "name": "絹ごし豆腐", "amount": "1丁", "kind": "main" },
        { "name": "にんじん", "amount": "1本", "kind": "main" },
        { "name": "卵", "amount": "2個", "kind": "main" },
        { "name": "だしの素", "amount": "小さじ1", "kind": "seasoning" }
      ],
      "steps": [
        "にんじんを細切りにし、絹ごし豆腐を水切りして角切りにする。",

}
```

**この応答が満たしていること:** 醤油・みりん・だしの素に `seasoning` が付いており、充足判定の対象にならない（D-1）／在庫の表記「豚こま肉」「絹ごし豆腐」がそのまま使われている（D-3）／期限が今日の豚こま肉が1件目の主材料になっている（FR-18）／炒めると煮るで調理法が分かれている（規則9）／卵に完全に火を通す手順がある（FR-20）。

**在庫にない「しょうが」が `main` で1件だけ追加されている。** これは規則3の範囲内であり、FR-17 では不足材料として表示される。**調味料は不足材料に数えない**ので、この献立の不足は1件である。

## 6. 応答の検証規則（腐敗防止層）

`MealResponseParser` の責務（ADR-005）。**ここを通らなかったものはドメイン層に渡らない。**

### 6.1 段階

| 段階 | 内容 | 失敗時 |
| --- | --- | --- |
| 1. 抽出 | 応答文字列から JSON 部分を取り出す。コードブロックの記号や前置きが付いていても、最初の `{` から対応する `}` までを取る | 失敗 |
| 2. 構文 | JSON として解析する | 失敗 |
| 3. 構造 | `meals` が配列であること | 失敗 |
| 4. 件数 | 下表の通り | 下表の通り |
| 5. 各献立の検証 | 下表の通り。**1件でも通らなければその献立だけを捨てる** | 件数の再判定へ |
| 6. 正規化 | 下表の通り | — |

規則1で「コードブロックの記号を書かない」と指示していても段階1を実装するのは、**指示の遵守を前提にした解析が最も壊れやすい**ため。指示は出力トークンの節約として意味があり、解析の保証としては当てにしない。

### 6.2 献立ごとの検証

| 項目 | 規則 | 違反時 |
| --- | --- | --- |
| `title` | 文字列。前後の空白を除いて1文字以上、40字以内 | 献立を捨てる |
| `title` | 同じ応答内で重複しない | 後に出たものを捨てる |
| `title` | **直前の提案に含まれていた献立の名称**と完全一致しない | 献立を捨てる（FR-36。新しさを求めた操作で同じものを返さない） |
| `ingredients` | 配列。1件以上12件以内 | 献立を捨てる |
| `ingredients[].name` | 文字列。1文字以上30字以内 | その材料を捨てる |
| `ingredients[].amount` | 文字列。0文字を許し、その場合は分量なしとする。30字以内 | 空文字に丸める |
| `ingredients[].kind` | `'main'` か `'seasoning'`。**それ以外・欠落は `'main'` に倒す**（C-16） | `'main'` に丸める |
| `ingredients` | **`'main'` が1件以上残ること**（C-16 / `Meal` の不変条件） | 献立を捨てる |
| `steps` | 配列。1件以上8件以内 | 献立を捨てる |
| `steps[]` | 文字列。1文字以上150字以内 | その手順を捨てる |
| 余分なフィールド | 無視する | — |

`title` 40字・`steps` 8件・150字は、**プロンプトの指示（30字・6件・60字）より緩い。** 指示は出力を短く保つためのもので、検証は壊れていないものを落とさないためのもの。役割が違うので値を揃えない。

### 6.3 正規化

| 対象 | 処理 |
| --- | --- |
| 全文字列 | 前後の空白を除去 |
| `ingredients[].kind` | **常備調味料リスト（D-1）に完全一致する `name` は、申告によらず `'seasoning'` に倒す** |
| `ingredients[].kind` | 上記以外は申告に従う。**リストにない調味料も `'seasoning'` のまま受け入れる** |
| `ingredients` | 同じ `name` が複数あれば最初の1件だけ残す |
| `steps` | 除去の結果0件になったら、その献立を捨てる（`Meal` の不変条件） |

固定リストによる `'seasoning'` への倒し込みを検証側にも置くのは、**D-1 が守られなかったときに再利用の仕組みが静かに壊れる**ため。プロンプトの遵守に依存させない。

**倒し込みは片側だけである。** リストにあるものを `'seasoning'` にはするが、リストにないものを `'main'` に戻すことはしない。**そうしないとリストが再び調味料の上限になり、ADR-023 で解いた問題が戻ってくる。**

### 6.4 件数の扱い

| 状況 | 扱い |
| --- | --- |
| 検証を通った献立が `requiredCount` より多い | **先頭から `requiredCount` 件を採用する。** 余りは捨て、保存もしない。どの件を残すかは応答の並び順で決める — **ACL は充足を判定できない**ため（D-4）、他に決定的な選び方がない |
| ちょうど `requiredCount` 件 | 採用 |
| 1件以上だが `requiredCount` 未満 | **その件数で提案を組む。** `Suggestion.entries` は1件以上3件以下なので成立する（C-15）。再試行しない（決定済み。第12章 論点1） |
| 0件 | 失敗として扱う |

> **C-2 との関係を明確にしておく。** C-2 は「生成した3件はすべて提示する。生成件数と提示件数は常に等しい」と定めるが、**ここでいう「生成した献立」は検証を通って `Meal` になったものを指す。** ACL が捨てた応答は献立になっていないため、C-2 の対象外である。4件返って3件を提示する場合も、1件しか通らず1件を提示する場合も、**`Meal` になったものはすべて提示されている。**

> **打ち切りは検証の失敗として現れる。** 応答が `max_tokens` に達すると JSON が途中で切れ、段階1か2で落ちる。**停止理由を記録しておかないと、プロバイダの形式不良と区別できない**（第7章の最大出力トークンを参照）。

### 6.5 失敗時

ADR-005 の通り、**自動リトライは行わない。** ユーザーに再試行の手段を提示する（NFR-07）。

- 生成の失敗は在庫の閲覧・保存済みの献立の閲覧に影響しない（NFR-06）
- 失敗した応答は保存しない（C-1 の裏返し）
- 失敗の回数は NFR-C2 の1日の生成回数に**数える**。数えないと、失敗を繰り返す経路が上限を素通りする

## 7. 呼び出しパラメータ

プロバイダ非依存の意図として記す。名称は各社の API に読み替える。

| 項目 | 値 | 理由 |
| --- | --- | --- |
| 温度 | **プロバイダによっては指定できない** | 下の ⚠ を参照。指定できる場合は高め（1.0 相当）にする |
| 最大出力トークン | 8192 | **思考のトークンもこの枠を消費する。** 現行世代の Claude は指定しなければ推論が既定で働き、その分が出力トークンに乗る。3件分の見積り（第10章）は1,100〜1,400だが、そこに合わせて切り詰めると**打ち切りが JSON 破損として現れる**。余裕を取り、実測してから下げる |
| 構造化出力の強制 | プロバイダの機能があれば使う | ADR-019 の比較軸(1)。**ただし使えても第6章の検証は省かない** |
| 推論の深さ | 浅く（`effort` に相当する設定があれば `low`） | 献立の生成は難しい仕事ではない。既定のまま深く考えさせると、**出力トークンと待ち時間が理由なく増える** |
| 応答の先頭を `{` に固定する手法 | **使えない前提で設計する** | Claude の現行世代では assistant の先頭固定が 400 になる。第6章の抽出（段階1）がこれを吸収する |
| プロンプトキャッシュ | **モデル次第。適用してから確かめる** | 下の 10.3 を参照 |

> ⚠ **温度を指定できないモデルがある。** Claude の現行世代（Opus 5 / Sonnet 5 など）は `temperature` / `top_p` / `top_k` を受け付けず、送ると 400 になる。**「温度を上げて多様性を出す」という設計は、そのままでは成立しない。**
>
> 代わりに多様性を担うのは **D-6 の避けたい献立の一覧**である。直前に提示した献立を必ず先頭に入れることが、FR-36 の「新しさ」を作る唯一の確実な手段になる。**これは D-6 の価値を上げる。**

**タイムアウトは Cloudflare Workers の制限に合わせる**（ADR-015）。生成が制限に収まらない場合、ストリーミングか非同期化への切り替えが必要になる。これは実装初期に測る（CLAUDE.md の必須事項）。

## 8. 生成を呼ばない条件

プロンプト設計の一部として、**そもそも投げない場合**を定める。

| 条件 | 扱い |
| --- | --- |
| プロンプトに載る在庫が0件（D-5 で全件落ちた場合を含む） | 呼ばない。在庫の登録・更新を促す |
| プロンプトに載る在庫が1件 | 呼ばない。**1食材で主菜3件は成立しない。** 在庫の追加を促す |
| **作れる既存の献立が1件以上ある** | 呼ばない。その1〜3件をそのまま提案とする（**ADR-022**。ここが最も効く経路） |
| 利用者が新しい献立を明示的に求めた | **呼ぶ。** ただし上書きするのは**すぐ上の「作れる既存の献立がある」条件だけ**である。在庫の条件と NFR-C2 の上限は、この場合も適用する（FR-36） |
| NFR-C2 の1日の上限に達している | 呼ばない。上限に達した旨を伝える |

在庫2件を境界にした理由: 2件あれば主菜が組める（例: 卵とにんじん）。1件は「ゆで卵」しか出ず、提案として無意味である。**この境界は試行（第9章 P-4）で見直す。**

## 9. 試行の設計

README の「これからやること 1」のうち、**プロバイダを決めずに実施できる部分**。以下のパターンで同一プロンプトを流し、第11章の表を埋める。

**実行するツールは `tools/prompt-trial/` にある。** 本章のパターンと第6章の検証規則、第9.2章の測定を実装済みで、API キーなしでも `--dry-run` と `--self-test` は動く。使い方は同ディレクトリの `README.md`。

### 9.1 在庫パターン

| # | 名前 | 在庫 | 何を見るか |

| **P-3** | 極端に少ない | 2件。卵4個・玉ねぎ2個 | 第8章の境界。**3件生成させたときに無理な献立が出るか**、出るならどう不自然か |

| **P-7** | 表記ゆれを含む | P-2 の在庫の食材名を「豚こま」「キャベツ（1/4）」等の崩れた表記にする | D-3 が崩れた表記でも守られるか。**守られないなら食材カタログ（Q-4）の優先度が上がる** |

### 9.2 評価の観点

| 観点 | 測り方 | 満たすべき水準 |
| --- | --- | --- |
| **形式の妥当性** | 第6章の検証を通過した応答の割合 | **95%以上。** ADR-019 の比較軸(1)そのもの。ここが低いプロバイダは他が良くても採らない |
| **材料名の一致** | **主材料**のうち、在庫の表記と完全一致した割合 | **95%以上。** C-6 と ADR-022 の再利用に直結する |
| **種別の誤り** | 常備調味料リストの語が `'main'` と申告された件数 | **限りなく0に近いこと。** D-1 の保険が働いた回数であり、**多いなら規則5の書き方を疑う** |
| **調味料の判別** | リストにない調味料（オイスターソース等）が `'seasoning'` と申告された割合 | **90%以上。** ここが低いと ADR-023 の利点が出ない。**人が目視で数える** |
| **期限の遵守** | 残日数1日以内の食材が、1件以上の献立で**主材料**として使われた割合 | **90%以上。** FR-18。判定の範囲は規則6（「期限は今日」と「あと1日」）に合わせる |
| **重複の回避** | `avoidTitles` と意味的に同じ献立が出た割合（**人が判定する**） | **10%以下。** FR-42 は努力目標なので0%を求めない |
| **調理法の分散** | 3件の調理法が3種類に分かれた割合 | 80%以上 |
| **不足材料の件数** | `MealCoverageService` 相当の判定を主材料だけで行い、不足材料の中央値を取る | **中央値1件以下。** 多いと FR-17 の表示が使い物にならない |
| **選べるか** | 「今日これを作るか」と自問して1件以上ある割合 | 要件定義 2.2 の判断基準2。**数値ではなく所感を書く** |
| 入力トークン | 第10章 | — |
| 出力トークン | 第10章 | — |
| 応答時間 | 実測 | ADR-019 の比較軸(4)、ADR-015 の制限 |


## 10. 費用の実測

要件定義 6.3 の試算は概算である。**この設計が固まった今、実測に置き換える。**

### 10.1 手順

1. 第4章のシステムプロンプトと、第9章の各パターンから組み立てたユーザーメッセージを用意する
2. プロバイダのトークン計測 API（Claude なら `count_tokens`）で**入力**トークンを測る
3. 実際に生成を1回行い、応答の `usage` から**出力**トークンを読む
4. パターンごとに記録し、6.3 の表を更新する

### 10.2 設計時点の見積り

実測前の目安。**この数値を根拠に判断しないこと。**

| 部位 | 概算 |
| --- | --- |
| システムプロンプト（第4章） | 約1,050トークン（1,398文字） |
| 在庫20件 | 約250トークン |
| 避けたい献立50件 | 約600トークン |
| 入力合計（P-5 相当） | **約1,900トークン** |
| 出力（3件・手順6ステップ・種別つき） | **約1,100〜1,400トークン** |

**要件定義 6.3 の前提（入力1,000／出力2,000）とずれる。** 入力は避けたい献立の分だけ増え、出力は NFR-C3 の制約（手順6ステップ・60字）の分だけ減る。**費用の合計は概ね同じ桁**だが、内訳が違うので実測時に前提ごと書き換える。

### 10.3 プロンプトキャッシュの判断

最小キャッシュ長はモデルごとに違い、**世代が新しいほど短いとは限らない**。システムプロンプトは約1,050トークンなので、ちょうどこの境界にかかる。

| モデル | 最小キャッシュ長 | 約1,050トークンのシステムプロンプトは |
| --- | --: | --- |
| Claude Opus 5 | 512 | **キャッシュされる** |
| Claude Sonnet 5 | 1,024 | **境界上。実測しないと分からない** |
| Claude Haiku 4.5 | 4,096 | されない |

つまり **NFR-C4 の可否はモデル選定と連動する。** 安いモデルを選ぶとキャッシュが効かず、高いモデルを選ぶと効く — 費用の比較をするとき、この向きを取り違えないこと。

> ⚠ **ADR-023 でシステムプロンプトが約2割伸び、Sonnet 5 の最小長（1,024）をまたぐ位置に来た。** 1,050 はあくまで文字数からの概算なので、**`--count-tokens` で実測するまで「される」と書かない。** プロンプトを1行足すたびにこの判定が変わりうる。

- 適用してみて `cache_read_input_tokens` がゼロなら**諦める**（NFR-C4 の指示通り）
- キャッシュのために意味のない文字列でシステムプロンプトを膨らませない。**入力トークンが増えて逆効果になる**
- そもそも本アプリの生成は**1日に数回**である。5分の保持時間ではほぼ確実に切れており、**キャッシュが効く場面はほとんどない**。NFR-C4 が Could に置かれているのは妥当

> 単価は Anthropic のリファレンス（2026-06-24 時点）による。**モデルの改廃で変わるため、決定時に確認する。**

## 12. この設計から差し戻す論点

**勝手に決めずに、判断を仰ぐもの。**

### 論点1　生成が `requiredCount` に満たない場合　`決定済み（v0.4 で改訂）`

**決定: 1件でも検証を通れば、その件数で提案を組む。** 3件に満たなくても失敗させない。0件のときだけ失敗として扱う。

| 案 | 内容 | 判断 |
| --- | --- | --- |
| A | 提案の組み立てごと失敗させ、再試行を促す | **不採用（v0.4 で撤回）。** 手元に使える献立があるのに何も出さないのは、利用者にとって最も損な選択である |
| B | 不足分だけ自動で再生成する | 不採用。待ち時間と費用が増え、ADR-005 の「自動リトライを行わない」と衝突する |
| **C** | 通った件数で提案を組む（1〜3件） | **採用** |

C を採る理由:

- **ADR-022 で `Suggestion.entries` が「1件以上3件以下」に緩んだ**。1〜2件の提案は再利用の経路ですでに起きるため、**生成の経路だけ3件を強制する理由がない**
- **利用者にとって、1件出るほうが0件より良い。** 明示操作で3件を求めた場面でも、画面には新しい献立を求める導線が残っている（FR-36）。**足りなければもう一度押せる** — 押すかどうかは利用者が決める。ADR-022 と同じ分担である
- 失敗の経路が減り、NFR-07 の再試行導線に頼る場面が「0件」だけになる

実装上の帰結:

- 採用した1〜2件は**保存する**（C-1）。捨てた応答は `Meal` になっていないので保存の対象外
- 生成の呼び出しは、成否によらず NFR-C2 の1日の回数に数える（6.5 と同じ）
- **`origin` は `'generated'` のまま。** 件数が3件に満たないことは、再利用が起きたことを意味しない

> 発生頻度は P-3（在庫2件）と P-6（野菜のみ）の試行で測る。**頻発するならプロンプトの問題**であり、件数の扱いではなく第4章の指示を直す。

### 論点2　C-13 と C-4 の衝突　`解消`

**ADR-022 により前提が消えた。C-4 への追記は不要。**

この論点は「同じ提案の中で、再利用した献立と生成した献立が同じ `Meal` を指しうる」という衝突だった。**ADR-022 で再利用と生成が同居しなくなったため、この経路は存在しない。**

生成のみの提案の中では、C-4 が同じ `mealId` を2度返すことはない — 応答内で `title` の重複を弾いており（6.2）、名称が異なれば参照先の既存の献立も異なるためである。

> 記録として残す。**組み立てを混ぜないという判断が、費用と体験のためだけでなく、不変条件を守る経路としても効いている。**
>
> なお、生成した献立の名称が既存と完全一致した場合の扱いは C-4 / C-4c にある。**既存を参照するが `origin` は `'generated'` のまま**であり、照合を行うのはユースケース層である（腐敗防止層は既存の献立を知らない）。

### 論点3　常備調味料リストの置き場所　`決定済み`

**決定: プロンプト側（D-1）に置き続ける。食材カタログには調味料を載せない。**

カタログ（Q-4）に調味料を含めない方針が確認されたため、二重管理は起きない。

> **ADR-023 でリストの役割が変わった。** かつては「調味料の唯一の定義」だったが、いまは**申告の誤りに対する保険**である。調味料かどうかを最終的に決めるのは生成側の `kind` であり、**リストは調味料の集合を閉じない。** この論点の決定（プロンプト側に置く）は変わらない。

| 帰結 | 内容 |
| --- | --- |
| カタログが未整備でも D-1 が働く | 再利用の仕組み（ADR-022）がカタログの整備状況に依存しなくなる。**この論点で最も価値のある結果** |
| 調味料は入力サジェストに出ない | FR-02 の補完対象外。在庫として登録したい場合は自由入力（FR-03）になる |
| FR-07 のカテゴリ「調味料」との関係 | カテゴリの選択肢としては残してよい。カタログに登録された食材の分類と、在庫の自由入力は別の話である |

### 論点4　`avoidTitles` の上限50件（Q-6 に接続）　`暫定で確定`

**決定: 50件のまま進める。ただし P-5 の試行で妥当性を測り、必要なら見直す。**

第10章の見積りでは、50件で入力トークンの約3分の1を占める。**削れるなら効果は小さくない**が、削って重複が増えれば FR-42 が形骸化する。

測り方は決まっている — P-5 で件数を **0 / 20 / 50** と変え、重複の回避率（9.2）と入力トークンの両方を記録する。**この3点が取れれば Q-6 は数字で閉じられる。**

### 論点5　分量を「2人分」に固定してよいか　`決定済み`

**決定: MVP は2人分に固定する。将来、選べるようにしてよい。**

要件定義の第10章（将来拡張）に「分量の選択」として記載した。MVP のスコープ外であり、**いま設定項目を作らない**（要件にない機能を足さない）。

将来これを入れるとき、プロンプト側で変わるのは第4章 規則2の一語だけである。**献立は生成時の分量のまま不変（C-3）**なので、設定を変えても過去の献立は変わらない。これは仕様として正しい — 履歴は生成時のまま残すべきものである（FR-30）。
