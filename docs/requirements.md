## 1. 背景と課題

**平日の夕方に「今日何作ろう」を考えるのが面倒くさい。** これが本アプリの出発点である。

献立が決まらない理由は、選択肢が多すぎることではなく、**制約（今ある食材）を思い出しながら考えなければならない**ことにある。

- 冷蔵庫の中身は開けないと分からず、**在庫を前提に献立を考えられない**。
- レシピサイトは「作りたい料理」から探す作りになっており、「**今あるもので何が作れるか**」の方向に向いていない。
- 結果として、決めるのを諦めて外食・惣菜になるか、決めてから買い物に行くことになる。

在庫管理アプリ単体では「記録が面倒なわりに得るものが少なく」続かない。本アプリは、**記録の見返り＝献立が決まること**をセットで提供する。

## 2. 目的とゴール

### 2.1 プロダクトゴール

**「今日の献立を考える」という毎日の判断コストをなくす。**

冷蔵庫の在庫を登録しておくと、アプリが在庫を前提とした献立候補を提示する。ユーザーは考えるのではなく**選ぶだけ**でよい状態にする。

### 2.2 成功の判断基準

数値目標は現時点では置かない。個人利用のプロダクトであり、精緻な KPI 設計より「自分が使い続けたいか」の方が信頼できる指標になるためである。以下を判断基準とする。

| # | 判断基準 |
| --- | --- |
| 1 | **自分が週に数回、実際に開いて使っているか** |
| 2 | 提示された候補から「これにしよう」と決められることがあるか。毎回スルーされるなら提案の質が要件を満たしていない |
| 3 | 在庫の登録が、面倒で放置されるほどの負担になっていないか |

> リリース後、上記のうち2と3が満たせていない場合に限り、原因を特定するための計測（提案の採用率、登録の離脱率）を追加で設計する。**最初から計測基盤を作り込まない。**

### 2.3 やらないこと（Non-Goals）

MVP では以下をスコープ外とする。

- 栄養計算・カロリー管理・健康アドバイス
- **食品ロス削減を主目的とした機能**（廃棄記録の集計・レポート等）。ただし 5.2 の期限管理は「使える食材を把握する」ために必要なので実装する
- 買い物リストの自動生成、ネットスーパー連携、価格比較
- 家族間でのリアルタイム共有（世帯の共有は FR-44〜FR-47 で扱うが、他の端末の変更を即時に反映することはしない）
- レシピの投稿・共有などのコミュニティ機能
- 冷蔵庫内カメラ・IoT 機器との連携

## 3. スコープと利用者

### 3.1 対象ユーザー

**個人または家族の利用（1世帯 = 1冷蔵庫）**。世帯は複数の利用者で共有でき、招待リンクで参加する（FR-44〜FR-47 / 第8章）。

#### ペルソナ

| 項目 | 内容 |
| --- | --- |
| 名前 | 30代・共働き会社員 |
| 状況 | 平日は帰宅が20時前後。週末にまとめ買いをする |
| 課題 | 帰宅時点で疲れており、献立を考える気力がない。冷蔵庫を開けて眺めても決まらず、結局いつもの数品か惣菜になる |
| 期待 | 「今ある食材でこれが作れる」を、考える前に提示してほしい |

### 3.2 対応環境

- スマートフォンのブラウザを主用途とする **レスポンシブ Web アプリ**。**PWA として提供し、ホーム画面に追加して使えるようにする**（5.7）。
- 台所での片手操作を想定し、モバイルファーストで設計する。
- ネイティブアプリは MVP スコープ外。ただし将来対応できるようアーキテクチャ側で備える（ADR-003）。
- **オフラインでのデータ操作は行わない**（ADR-016）。

## 4. 用語定義

| 用語 | 定義 |
| --- | --- |
| 食材（Ingredient） | 「にんじん」「豚こま肉」などの**種類**を表すマスタ上の概念。**MVP ではマスタを置かない**（11章 論点4） |
| 在庫（StockItem） | ユーザーの冷蔵庫にある**個々の実体**。食材を参照し、数量・期限を持つ |
| 献立候補（Suggestion） | 在庫を元に生成され、ユーザーに提示された献立 |
| 期限 | 賞味期限・消費期限を区別せず、単一の「使い切りたい日」として扱う（**2026-09-23 にユーザーが決定**。11章 論点5） |

## 5. 機能要件

優先度は MoSCoW（Must / Should / Could）で示す。**Must が MVP のリリース範囲**である。

### 5.1 食材の登録・管理

| ID | 要件 | 優先度 |
| --- | --- | --- |
| FR-01 | 食材を**手入力**で登録できる。入力項目は「食材名（必須）」「数量＋単位」「期限」「献立に使う（必須。既定はオン）」 | Must |
| FR-02 | 食材名は入力途中で**サジェスト（インクリメンタル補完）**され、**その世帯が過去に入力した食材名と、保存済みの献立の材料名**から選択できる（マスタは置かない。11章 論点4） | Must |
| FR-03 | 補完に出てこない食材名は、そのまま自由入力で登録できる（登録がブロックされない） | Must |
| FR-04 | 在庫を一覧表示できる。既定は**期限が近い順**でソートする | Must |
| FR-05 | 在庫の数量・期限・「献立に使う」を編集できる | Must |
| FR-06 | 在庫を削除できる | Must |
| FR-07 | 在庫をカテゴリ（肉・魚・野菜・調味料など）で絞り込める | Should |
| FR-08 | 複数の食材をまとめて1画面で連続登録できる（買い物後の一括入力） | Should |
| FR-09 | よく使う食材をテンプレートとして保存し、ワンタップで登録できる | Could |
| FR-10 | 在庫の削除時に「使い切った」「捨てた」を選択でき、記録として残せる。既定は「使い切った」とし、1タップで完了できること | Could |

**入力項目から「保存場所」を削除した（v0.2）。** 判断の理由は 5.5 に記す。

**FR-10 について**: 廃棄削減は本アプリの目的ではないため Could に置く。ただし「一定期間廃棄しなかったら何かある」という将来案（第10章）は、**この記録がなければ後から実装できない**。実装する場合は既定値を「使い切った」にして、操作を1タップ増やさないことを条件とする。

### 5.2 期限管理

期限管理は「食品ロス削減」のためではなく、**「今日使うべき食材」をサジェストの入力にするため**に必要である。

| ID | 要件 | 優先度 |
| --- | --- | --- |
| FR-11 | 期限までの残日数を在庫一覧に表示する | Must |
| FR-12 | 期限が近い在庫を視覚的に区別する（例: 3日以内=警告、当日/超過=危険） | Must |
| FR-13 | 期限は任意入力とし、未入力でも登録できる。未入力の在庫は期限による警告・優先の対象外とする | Must |
| FR-14 | 期限切れ間近の在庫をまとめて確認できる画面またはセクションを持つ | Should |
| FR-15 | 期限が近い食材について通知（プッシュ／メール）を送る | Could |

**FR-13 の意図**: 期限を必須にすると登録が面倒になり、2.2 の判断基準3を損なう。記録の心理的コストを最優先する。

### 5.3 献立サジェスト

本アプリの中核機能。実現方式は **LLM による生成**に決定（第6章）。

| ID | 要件 | 優先度 |
| --- | --- | --- |
| FR-16 | 現在の在庫を元に、献立を**複数件（3件程度）**提示できる。**ただし提案は1〜3件になりうる** — 再利用で作れる献立が3件に満たない場合（FR-34 / ADR-022）と、生成結果が3件に満たない場合がある | Must |
| FR-17 | 各候補について「在庫でまかなえる材料」と「不足している材料」を区別して表示する | Must |
| FR-18 | 候補は**期限が近い在庫を優先的に使うもの**を含むよう生成する | Must |
| FR-19 | 各候補について、作り方の手順を表示できる | Must |
| FR-20 | 生成された献立には**「AIによる提案です。分量・加熱時間はご自身で確認してください」に相当する注意表示**を行う | Must |
| FR-21 | 生成した献立は保存され、再訪時に**同じものが表示される**。再生成は明示的な操作（FR-36）でのみ行う | Must |
| FR-22 | 候補から実際に作った献立を「作った」として記録でき、使用した在庫を消費として反映できる | Should |
| FR-23 | 特定の在庫を指定して「これを使う献立」を生成できる | Should |
| FR-24 | 「不足材料が0件のもののみ」を要求できる | Could |

**FR-20 の意図**: 調理は誤りが実害（食中毒・失敗）につながる領域である。LLM は存在しない分量や不適切な加熱時間を生成しうるため、注意表示は Must とする。

**FR-21 の意図**: LLM は同じ在庫でも毎回異なる結果を返す。ユーザーは「毎回違う献立が出るのは良い」としているが、それは**能動的に求めたとき**の話であり、「さっき見た候補が画面を戻ったら消えている」のは別物で、単なる不具合に見える。加えて、生成結果を保存して使い回すことは 6.3 のコスト設計における主要な削減手段でもある。**新規性は明示的な操作で提供し、既定は安定させる。**

#### 既存の献立の再利用

2回目以降の提案では、**すでに持っている献立で今日作れるものが1件でもあれば、それだけを出す**。**足りない分を生成で埋めることはしない**（ADR-022）。LLM を呼ぶのは、作れる献立が1件もないときと、利用者が明示的に求めたときだけである。

| ID | 要件 | 優先度 |
| --- | --- | --- |
| FR-34 | 提案を組むとき、既存の献立のうち**現在の在庫で不足なく作れるもの**が1件でもあれば、それだけを提示し、**LLM を呼ばない**。3件に満たなくても不足分を生成で埋めない（ADR-022） | Must |
| FR-35 | 再利用された献立は、新しく生成されたものと**区別して表示する**（例:「前に見た献立」の印） | Must |
| FR-36 | 新しい献立を求める明示操作を画面に置く。この操作は再利用を行わず、**常に3件を新規生成する** | Must |
| FR-37 | 直近の提案に出したばかりの献立は、再利用の対象から除外する | Should |

**FR-35 の意図**: 再利用を黙って混ぜると、ユーザーには「なぜ同じ献立がまた出るのか」としか映らない。**「前に見たこれ、今日の在庫で作れます」という提示にして初めて価値になる。** 表示を分けることは体験上の要請であって、実装の都合ではない。

**FR-36 の意図**: これは、ユーザーが明示的に新しさを求めた操作である。ここで再利用すると要求に応えていない。コスト削減はこの操作を除いた範囲で行う。

**FR-34 と FR-36 は対で成立する。** FR-34 により提案が1〜2件になる日があり、そのとき「もっと見たい」に応える手段が FR-36 である。**足りない分をアプリが勝手に生成して3件に揃えるのではなく、足りないと感じたユーザーが求める。** 既定の表示で LLM を一度も呼ばない経路は、この分担によって成立する。画面上の文言と配置は画面設計で決める。

**FR-34 の判断基準**: 再利用の対象は**不足材料が0件のものに限る**。1件でも足りない献立を再利用するくらいなら、新規生成のほうが良い提案になる。4件以上ある場合は上位3件を採る。詳細な判定順序はドメインモデル文書に定める。

| ID | 要件 | 優先度 |
| --- | --- | --- |
| FR-42 | 新しく生成する際、**すでに手元にある献立と同じものを提案しない**よう働きかける。具体的には既存の献立名を生成時の入力に含める | Must |
| FR-43 | 「献立に使う」がオフの在庫品は、**献立の提案（生成への入力と再利用の判定）に使わない**。在庫一覧・充足の表示・食材名の補完には残る（ADR-086） | Must |

**FR-42 の位置づけ**: これは**保証ではなく努力目標**である（ADR-021）。生成側に避けさせたうえで、生成のあとに判定モデル（Jev）で表記の違う同じ献立を落とす（ADR-089）。判定が返らない回は落とさずに出すので、重複が出ても壊れない設計は維持する。

### 5.4 アカウント・認証

| ID | 要件 | 優先度 |
| --- | --- | --- |
| FR-25 | ユーザーはアカウントを作成し、ログイン／ログアウトできる | Must |
| FR-26 | データは世帯ごとに分離され、他の世帯の利用者から参照できない | Must |
| FR-27 | ユーザーは自分のアカウントとデータを削除できる。世帯に自分しか居なければ世帯のデータも消え、他に居れば自分だけが抜けて消える | Must |
| FR-44 | 世帯の誰でも、他の利用者を世帯に招く招待リンクを作れる。リンクは1回限りで、24時間で切れる | Should |
| FR-45 | 招待リンクを開いた利用者は、確認を経て世帯に参加できる。**参加すると、その利用者の食材・献立・履歴は消え、招待した世帯のものに統一される。** このことを参加の前に画面で知らせる | Should |
| FR-46 | 世帯に他の利用者が居るとき、自分は世帯を抜けられる。抜けると空の世帯から始まる | Should |
| FR-47 | 設定画面に、冷蔵庫を共有している自分以外の人数を出す | Should |

### 5.5 決定記録: 保存場所（location）を持たない

**結論: MVP では保存場所を持たない。**

| 観点 | 評価 |
| --- | --- |
| 献立サジェストへの寄与 | **ほぼゼロ。** 「冷蔵か冷凍か」は何が作れるかを変えない |
| 在庫を探す助けになるか | **薄い。** 冷蔵庫を開ければ見える。場所を確認するためにアプリを開く動機がない |
| 入力コスト | **確実に増える。** 登録項目が1つ増え、しかも毎回選ばされる |
| 一覧の情報量 | 絞り込み軸が増えるが、個人の冷蔵庫（数十件規模）では絞り込む必要自体が薄い |

保存場所に唯一意味があるとすれば「**冷凍かどうか**」で、これは期限の桁が変わる（数ヶ月単位）ことと、解凍が必要で「今すぐ作れるか」に影響することを意味する。ただしこれは**必要になってから真偽値フラグ1つで足りる**話であり、4値の選択項目を最初から入力必須の位置に置く理由にはならない。

登録の手間は本アプリの最大の離脱要因（2.2 の判断基準3）であり、**寄与の薄い項目を削ることは機能を減らすのではなく、中核体験を守ること**である。

### 5.6 献立の履歴

生成した献立は捨てずに永続化し、ユーザーが過去に遡れるようにする。これは 5.3 の FR-21（生成結果の保存）を、単なるコスト対策から**機能として位置づけ直す**ものである。

> 中核の呼称は「献立 / `Meal`」に確定済み（ADR-018）。UI 上の文言は設計時に詰める。

| ID | 要件 | 優先度 |
| --- | --- | --- |
| FR-28 | 過去に提示された献立を、新しい順に一覧できる（**「以前見た献立」**） | Must |
| FR-29 | 「作った」と記録した献立を、新しい順に一覧できる（**「作った献立」**） | Must |
| FR-30 | 履歴の献立を開き、材料と手順を再度確認できる。表示内容は生成時と同一であること | Must |
| FR-31 | 履歴の献立から、その場で「作った」を記録できる（再度作った場合） | Should |
| FR-32 | 履歴の献立について、**現在の在庫での**充足状況を確認できる | Should |
| FR-33 | 献立を名称で検索できる | Could |

**FR-29 と FR-28 の関係**: 両者は別々のデータではなく、**同じ献立を調理記録の有無で振り分けたもの**である。一度でも作った献立は「作った献立」に移り、「以前見た献立」からは外れる。状態を二重に持たないことで、食い違いを構造的に防ぐ（`docs/domain-model.md` 第5章）。

**FR-30 の意図**: 履歴の献立は**生成時のまま不変**とする。LLM に再生成させて表示すると、同じ献立を開いたはずが内容が変わり、履歴としての意味を失う。

**FR-32 の意図**: 充足状況は献立に保存せず、開いた時点の在庫で毎回算出する。「先週作ったあれ、今日の在庫でも作れるか」に答えるための機能であり、保存された古い判定を見せても意味がない。

### 5.7 PWA

台所でサッと開けることが体験の前提になるため、ホーム画面に追加できる状態で提供する。

| ID | 要件 | 優先度 |
| --- | --- | --- |
| FR-38 | Web アプリマニフェストとサービスワーカーを備え、ホーム画面に追加して単独のアプリとして起動できる | Must |
| FR-39 | アプリの外枠（HTML・CSS・JS）をキャッシュし、2回目以降の起動を高速化する | Must |
| FR-40 | iOS ではワンタップのインストール導線を出せないため、**「ホーム画面に追加」の手順を案内する UI** を用意する | Should |
| FR-41 | オフライン時は、その旨を明示して操作を止める。**オフラインでの登録・編集は行わない** | Must |

**FR-40 の背景**: iOS の Safari は `beforeinstallprompt` を実装していないため、ネイティブのインストールバナーを出せない。利用者が自分で「共有 → ホーム画面に追加」をたどる必要があり、案内なしでは事実上インストールされない。

**FR-41 の意図**: オフラインでの書き込みを許すと、同期と競合解決が必要になり、MVP の規模を大きく超える。**PWA 化の目的はホーム画面への設置と起動の速さであって、オフライン動作ではない**（ADR-016）。

> **通知（FR-15）への影響**: iOS で Web プッシュ通知が届くのは、Safari から「ホーム画面に追加」でインストールされた場合のみで、ブラウザのタブで開いているだけでは届かない（iOS 16.4 以降）。期限通知は Could のまま据え置く。

## 6. 献立サジェストの実現方式【決定済み】

### 6.1 決定

**LLM による献立生成を採用する。**（プロバイダは Gemini。ADR-079 が ADR-019 を置き換えた）

### 6.2 決定の経緯

当初、以下4案を比較した。

| 案 | 概要 | 判断 |
| --- | --- | --- |
| A: 外部レシピAPI | 外部APIから候補取得＋自前スコアリング | **不採用**。下記の制約により成立しない |
| B: LLM生成 | 在庫を渡して献立を生成 | **採用** |
| C: 自前レシピDB | レシピを自分でDB化しマッチング | 不採用。初期データ投入の工数が許容できない |
| D: ハイブリッド | C を基本に B で補完 | 将来の選択肢として保持 |

#### 案A が成立しない理由: 日本語レシピの「材料検索」は事実上できない

在庫起点のサジェストの中核は「材料の集合からレシピを引く」検索だが、ここに構造的な制約がある。

- **楽天レシピAPI** は、公開されているのが「カテゴリ別ランキングAPI」と「カテゴリ一覧API」の2種類で、**材料名を投げてレシピを引く仕様になっていない**。取得件数にも制限があり、材料検索を行うには自前DBへの蓄積と索引付けが必要になる（＝実質的に案C）。
- **クックパッド**は、一般開発者向けの公開レシピ検索APIを提供していることが確認できなかった。前提にできない。
- **Spoonacular**（英語圏）は `findByIngredients` という用途に合うエンドポイントを持つが、レシピが英語圏の料理中心で、日本の家庭料理アプリとしての妥当性に難がある。

#### 案B を選ぶ理由

- **初期データが不要。** 案C の最大の障壁であるレシピDBの構築工数がゼロになる。
- **在庫の中途半端さに強い。** 「余り物3つ」のような状態でも何らかの提案が出る。これは案C/Dが最も苦手とする状況であり、かつ**実際に献立に困るのはまさにその状況**である。
- **結果が毎回変わることが、この用途では欠点にならない。** 献立提案において多様性は魅力として働く（ただし FR-21 の通り、変わるタイミングはユーザーが制御する）。
- 日本語・和食への対応が良好である。

### 6.3 コスト設計

「ランニングコストをなるべく安く」という要求に対し、以下を設計する。

#### 前提となる単価

| モデル | 入力 $/1M tokens | 出力 $/1M tokens |
| --- | --- | --- |
| Claude Opus 5 | $5.00 | $25.00 |
| Claude Sonnet 5 | $2.00 | $10.00 |
| Claude Haiku 4.5 | $1.00 | $5.00 |

#### 1回の献立生成にかかる費用の試算

以下は**概算であり、実測値ではない**。プロンプト設計が固まった段階で `count_tokens` による実測に置き換えること。

- 前提: 入力 約1,000 tokens（システムプロンプト＋在庫30件）、出力 約2,000 tokens（3件＋手順）、1ドル150円換算。**単価は Claude のものを暫定で用いた** — 試算の時点ではプロバイダが未決だった。決定後のプロバイダと単価は 11章 3（ADR-079）。

| モデル | 1回あたり | 1日1回 / 月30回 |
| --- | --- | --- |
| Claude Opus 5 | 約 $0.055（約8円） | 約 $1.65（約250円） |
| Claude Sonnet 5 | 約 $0.022（約3円） | 約 $0.66（約100円） |
| Claude Haiku 4.5 | 約 $0.011（約2円） | 約 $0.33（約50円） |

**重要な示唆: 個人利用である限り、モデル選定はコスト上の主要因ではない。** 最上位モデルでも月250円程度に収まる。したがって**まず提案の質が最も高い構成で作り、コストが問題になってから下げる**のが合理的である。逆に、公開して利用者が増えた場合は**ユーザー数に線形にコストが増える**ため、そこが本当の分岐点になる。

#### コスト削減の要件

| ID | 要件 | 優先度 |
| --- | --- | --- |
| NFR-C1 | 生成結果を保存し、**在庫に変化がない限り再生成しない**（FR-21 と同一の仕組み） | Must |
| NFR-C1b | 在庫が変化した場合も、**既存の献立で作れるものが1件でもあれば LLM を呼ばない**（FR-34 / ADR-022） | Must |
| NFR-C2 | 1世帯あたりの1日の生成回数に上限を設ける（初期値10回程度） | Must |
| NFR-C3 | 出力トークン量を要件から制御する。手順は簡潔な形式を指定し、冗長な生成を防ぐ | Should |
| NFR-C4 | システムプロンプトが十分な長さに達する場合、プロンプトキャッシュを適用する | Could |

**NFR-C1 と NFR-C1b が最も効く。** 献立を1日に何度も作り変えるユーザーはいないためキャッシュのヒット率は高く、さらに使い続けるほど手持ちの献立が増え、再利用で賄える割合が上がっていく。**利用期間が延びるほど1回あたりの費用が下がる**構造になる。

**NFR-C4 の注意点**: プロンプトキャッシュには最小キャッシュ長（モデルにより 512〜4096 tokens）があり、**短いシステムプロンプトはキャッシュされない**。本アプリのプロンプトは短くなる見込みで、効果が出ない可能性が高い。実装時に `usage.cache_read_input_tokens` で実際にヒットしているかを確認し、ゼロなら適用を諦めること。

#### 見落としやすいコスト

LLM の呼び出し費用よりも、**ホスティングとデータベースの固定費**の方が大きくなる可能性が高い。技術選定（第11章）の際に、無料枠のある構成を優先して評価すること。

### 6.4 案D への移行余地

将来、以下のいずれかが起きた場合、案D（自前DB＋LLM補完）への移行を検討する。移行時にスキーマの作り直しが起きないよう、第8章のデータモデルは案B/D 両対応で設計する。

- 公開して利用者が増え、生成コストが許容額を超えた場合。
- ユーザーが「作った」と記録した献立が蓄積し、**それ自体が自前レシピDBの初期データになった**場合（FR-22 がこの布石になる）。

## 8. データモデル

**構造の正は `docs/domain-model.md` にある。** 本書では要件との対応のみを示す。

| 概念 | 役割 | 対応する要件 |
| --- | --- | --- |
| 世帯（Household） | 冷蔵庫の単位。全データの所有者。複数の利用者で共有でき、利用者は招待リンクで参加する（ADR-087） | FR-26、FR-44〜FR-47 |
| 在庫品（StockItem） | 冷蔵庫にある1件の食材。同じ食材でも統合しない | FR-01〜FR-13 |
| 食材（Ingredient） | カタログ上の食材の種類。名寄せに使う。**MVP では置かない**（11章 論点4） | — |
| 献立（Meal） | 生成された1つの献立。**永続化され、履歴として再表示される実体** | FR-16〜FR-21, FR-28〜FR-33 |
| 提案（Suggestion） | 1回の提案で得られた献立1〜3件と、そのときの在庫スナップショット（ADR-022） | FR-16, FR-21 |
| 調理記録（CookingRecord） | 献立を作ったという記録。**「以前見た」と「作った」を分ける唯一の事実** | FR-22, FR-29, FR-31 |

### 8.1 要件に効く設計判断

以下は要件の解釈に直結するため、本書にも記す。根拠は `docs/adr.md` の各 ADR にある。

- **全データを世帯に持たせる**（ADR-087）。在庫を利用者に直接ぶら下げると、共有のために全テーブルと全クエリの改修が必要になる。
- **在庫品を統合しない**（ADR-007）。同じ食材を別の日に買えば期限が違うため、一覧に同じ食材名が複数行並ぶ。これは仕様である。
- **献立は生成後に編集できない**（ADR-006）。FR-30 の「生成時と同一」を保証するための制約。
- **充足判定を保存しない**（ADR-009）。FR-32 の通り、開いた時点の在庫で毎回算出する。
- **分量を構造化しない**（ADR-010）。数量の演算をする要件がないため自由文字列とする。結果として「不足量」は出せず、不足は食材の有無でのみ判定する。

## 9. 非機能要件

技術スタックが未定のため、実装手段ではなく**満たすべき性質**として記述する。コスト関連の要件は 6.3（NFR-C1〜C4）に記載。

### 9.1 性能

| ID | 要件 |
| --- | --- |
| NFR-01 | 在庫一覧の初期表示は、在庫100件までで2秒以内（モバイル回線を想定） |
| NFR-02 | 食材登録の保存操作は1秒以内に完了応答を返す |
| NFR-03 | 保存済みの献立候補（FR-21）の表示は2秒以内。LLM の呼び出しを伴わないこと |
| NFR-04 | 献立の新規生成は、処理中であることを明示するUIを表示する。生成には数十秒を要する場合がある |

**NFR-03 と NFR-04 の分離が要点である。** 毎回の閲覧が LLM の応答待ちになると、体験が成立しない。「保存済みの表示は速い／新規生成は待たせてよい」を明確に分けること。

### 9.2 可用性・信頼性

| ID | 要件 |
| --- | --- |
| NFR-05 | 在庫データは日次でバックアップされ、障害時に復旧できる |
| NFR-06 | LLM API の障害・レート制限時も、**在庫の登録・閲覧と、保存済み献立の閲覧は継続して利用できる**。新規生成のみ縮退し、その旨をユーザーに伝える |
| NFR-07 | LLM の応答が期待する形式で得られなかった場合、アプリはエラーで停止せず、ユーザーに再試行の手段を提示する |

### 9.3 セキュリティ・プライバシー

| ID | 要件 |
| --- | --- |
| NFR-08 | 通信は全て暗号化する |
| NFR-09 | 認可はサーバ側で強制する。他ユーザー（他 Household）のデータには、URL を直接指定しても到達できない |
| NFR-10 | **LLM API キーをクライアント側に置かない。** 生成の呼び出しは必ずサーバ側を経由する |
| NFR-11 | LLM（生成した献立を確かめる判定モデル Jev を含む）に送信するのは在庫の食材名・数量・期限と献立名に限定し、ユーザーの氏名・メールアドレス等の識別情報を含めない |
| NFR-12 | パスワードを自前で保持する場合、平文で保存しない。外部の認証基盤に委譲する場合はこの限りでない |
| NFR-13 | FR-27 のアカウント削除時、関連する在庫・生成結果・ログを削除する |
| NFR-19 | 在庫品の食材名は30字以内、分量は15字以内とし、どちらも改行などの制御文字を含めない。サーバ側で断り、画面も同じ上限で入力を止める。生成への入力の構造を在庫の文字列で崩させず、生成側で使えない長さの名称を保存させないため |

**NFR-10 が最重要。** クライアントに API キーを置くと、第三者に抽出されて無制限に使用されうる。これはコスト要求に対する最大のリスクである。

**NFR-11 の意図**: 食生活は生活実態を推測できる情報である。外部送信の範囲を要件として固定しておく。

### 9.4 ユーザビリティ

| ID | 要件 |
| --- | --- |
| NFR-14 | 主要操作（在庫の登録・編集・削除）は片手で完結できるレイアウトとする |
| NFR-15 | 食材1件の登録は、名前入力から保存まで10秒以内で完了できる |
| NFR-16 | 主要画面は WCAG 2.1 レベル AA 相当のコントラスト比を満たす |
| NFR-17 | 期限の警告は色のみで表現せず、テキストまたはアイコンを併用する |

### 9.5 保守性

| ID | 要件 |
| --- | --- |
| NFR-18 | 献立生成のロジックは差し替え可能なインターフェースの背後に置き、案D（6.4）への移行時にアプリ全体の改修が発生しないようにする |
