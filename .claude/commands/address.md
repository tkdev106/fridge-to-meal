# /address — レビュー対応

レビューの指摘がすべて正しいとは限らない。**各指摘を批判的に評価し、妥当なものだけ直す。**

## 使い方

```
/address [PR番号 | URL]
```

- **無引数**: 直前の会話に含まれるレビュー内容を対象にする
- **数値 / URL**: その PR のレビューを取得する
  - `gh api repos/{owner}/{repo}/pulls/{番号}/reviews` — レビュー本文
  - `gh api repos/{owner}/{repo}/pulls/{番号}/comments` — コードへのインラインコメント
  - `gh` が使えない環境では GitHub の MCP ツールで同じものを取る

## 評価の観点

指摘ごとに、次の順で見る。**設計文書がレビューより強い。**

1. `CLAUDE.md` の4つの約束、`docs/domain-model.md` の確定事項 C-1〜C-16、`docs/adr.md` と
   矛盾しないか。矛盾する指摘は**直さない**（理由を書いて返す）
2. 技術的に正しいか
3. `docs/requirements.md` の FR / NFR の範囲内か。**範囲外の機能追加を求める指摘は直さない**
4. トレードオフとして妥当か

## 手順

1. 指摘を取得し、一覧にする
2. 各指摘を評価し、対応する／しないを決める
3. 対応するものだけ直す。直したら `pnpm verify`
4. サマリーを出す

```markdown
## レビュー対応サマリー

### 対応した指摘
| 指摘 | 修正内容 |
| --- | --- |

### 対応しなかった指摘
| 指摘 | 理由 |
| --- | --- |
```

5. 返信するかはユーザーに確認してから。**投稿前に必ず文面を提示する**

## 注意

- 指摘を鵜呑みにしない。ただし、**直さない理由はレビュアーが納得できる形で書く**
- 修正で新しい問題が出ていないか、`pnpm verify` の緑だけでなく差分を読み返して確認する
